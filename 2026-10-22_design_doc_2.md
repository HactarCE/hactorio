# hactorio design: values and facets

This document defines the language syntax and semantics. Autocomplete mechanics,
game-data import, saving, and architecture are in `2026-10-20_design_doc_1.md`.

## 1. Overview

A document is an ordered list of tabs. Each line is one statement, a comment, or
blank. Variables are tab-scoped and visible only to later lines in the same tab.
Variables may hold any value.

```
name = EXPR
EXPR
# comment
```

A definition that fails **evaluation** binds a poisoned value; references
propagate the original error. A **parse** failure does not bind the name, so a
later reference reports an unknown variable. A variable cannot be redefined or
shadowed within a tab.

### 1.1 Statements and identifiers

- Identifiers are `[A-Za-z_][A-Za-z0-9_]*`, case-sensitive, with no hyphens.
  `stack-size` is not an identifier; it exists only as the signal and property
  `:stack-size:` / `.:stack-size:`.
- Reserved words, unit words, and prototype ids cannot be variable names.
  Therefore `2 m` is two minutes, and `m` is never a variable.
- The metric suffixes `k`, `M`, and `G` are ordinary identifiers; they act as
  suffixes only immediately after a number.
- Forward references are errors; variables are visible only to later lines.
- `3s` and `3 s` both parse. Metric suffixes `k`, `M`, `G` are case-sensitive;
  `M` is mega, while `m` is minute.

## 2. Tokens

### 2.1 Prototype tokens

A prototype token has two interchangeable forms:

- plaintext: `:prototype-id:`
- one private-use codepoint assigned to the entry

Prototype ids use hyphens (`express-transport-belt`). Autocomplete inserts the
PUA form.

Prototype tokens cover items, fluids, modules, beacons, recipes, and equipment
items. An entry is a namespace entry; it may carry several facets (item,
machine, recipe).

### 2.2 Signals

Virtual signals are accepted as property selectors after `.`:

- `.:stack-size:` — the stack-size property; also usable as a prefix (§4.7)
- `.:clock:` — alias for `.time`
- `.:speed:` — alias for `.speed`
- `.:lightning:` — alias for `.electric`

They have no value semantics and are never offered as ordinary expression
values. `:stack-size:` additionally has the prefix form. Signals live in a
separate fixed-glyph table; see the implementation notes for PUA allocation and
save/load handling.

### 2.3 Numbers and punctuation

- Decimal numbers: `3`, `3.5`, `.5`. A trailing `3.` is not a valid number.
- Metric suffixes: `3k`, `1.5M`, `250G`.
- Comments start with `#` and run to the end of the line.
- A `.` followed by a digit is part of a number; otherwise `.` is property access.

Reserved words: `in`, `making`, `with`. The metric suffixes `k`, `M`, and `G`
are recognized only immediately after a number; elsewhere they are ordinary
identifiers.

### 2.4 Units

- Time: `s`/`second`, `m`/`minute`, `h`/`hour`; folded to seconds.
- Energy: `joule`/`J`; power: `watt`/`W` (= `joule/second`); craft count:
  `craft`.
- A number followed by a unit token or prototype token is a quantity literal.
- Belt abbreviations (`yb`, `rb`, `bb`, `gb`, `syb`, ...) and `@` machine specs
  are not part of this language. Use belt tokens with `:stack-size:` instead.

## 3. Values and facets

A value is a record of independent facets. A facet is present or absent; each
present facet has its own coefficient, count, or map.

| Facet | Meaning |
|---|---|
| `item` | a monomial: items, fluids, seconds, joules, crafts |
| `recipe` | a recipe reference from a prototype token |
| `machine` | a configured machine and optional count |
| `process` | a production process, solved or unsolved |
| `config` | module and beacon configuration |
| `belt` | how many belt tiles are represented |
| `rate` | an item stack rate or a fluid volume rate |
| `capacity` | item stack slots or fluid volume |

Examples:

- `:foundry:` — item + machine + recipe.
- `:transport-belt:` — item + belt + rate.
- `:steel-chest:` — item + capacity.
- `:speed-module-3:` — item + config.
- `:beacon:` — item + config.
- `1 :iron-plate: in :foundry:` — process only.

Initial facets by token kind (every item/fluid token also gets `recipe` when the
entry has a same-id recipe):

| Token kind | Additional facets |
|---|---|
| item / fluid | item |
| machine item | item + machine |
| module | item + config |
| beacon | item + config |
| belt | item + belt + rate |
| inserter | item + rate |
| item container (chest, car, cargo wagon) | item + capacity |
| fluid container (tank, fluid wagon) | item + capacity (fluid) |
| pump | item + rate (fluid) |
| equipment item | item (equipment metadata for power/energy) |
| recipe-only | recipe |

### 3.1 Facet rules

Each binary operator is applied per facet:

- **Scaling exception:** when one operand is a dimensionless scalar (`item:
  Some` with an empty monomial; §3.1.1), it scales every scalable facet of the
  other operand, even though the scalar does not carry those facets. This applies to
  multiplication and to division of a value by a dimensionless scalar. For a
  machine facet only the count scales; its per-machine module and beacon
  configuration is fixed. A separate config facet follows §3.6: it scales only
  by a nonnegative integer scalar and drops otherwise.
- Otherwise, a facet survives iff both operands have it and the operation is
  defined for those facet values.
- If a facet is present on only one operand (and the scaling exception does not
  apply), it is dropped.
- If both operands have the facet but the values are incompatible, the facet is
  dropped. This is not an error by itself.
- The isolated rate/capacity time conversions in §3.8, rate/capacity
  application to an item/fluid, process time arithmetic, and the
  `with`/`making`/`in`/`:stack-size:` rules in §4.4–§4.7 are exceptions to the
  one-sided-drop rule.
- If no facet survives, the whole operation is an error.
- Each facet has its own coefficient; facets do not share one scalar.

Operations that change a value's dimension (multiplication by units, powers,
belt application, `in`, `with`, `making`) can drop facets that no longer make
sense. `+`/`-` only combine like facets. A dropped facet produces no warning;
the details popup shows only the facets that survived.

When an operation drops every facet, the error names the operator, lists the
facets present on each operand, and states why each final facet was dropped
(unsupported operation, incompatible values, or missing counterpart). Example:
`(:foundry: with sm) * 2 s` cannot multiply a machine value by time; the
machine facet drops and no facets remain.

### 3.1.1 Value representation and dispatch

```
Value {
    item: Option<Monomial>,
    recipe: Option<RecipeId>,
    machine: Option<MachineFacet>,
    process: Option<Process>,
    config: Option<Config>,
    belt: Option<Belt>,
    rate: Option<RateFacet>,
    capacity: Option<CapacityFacet>,
}
```

A dimensionless scalar is `item: Some` with an empty monomial; it is not an
absent item facet. A process-only value has `item: None`. No value has every
field absent.

Coexistence is limited to combinations §3 and §4 construct:

- `process` is exclusive: a process-only value has every other field absent.
- `recipe` may coexist with `item` and/or `machine`, but not `process`.
- `machine` carries its own merged config; a separate `config` field never
  coexists with `machine`.
- `belt`, when present, is accompanied by `rate`.
- `rate` and `capacity` may coexist with `item` (a belt or chest token does).
- `config` may coexist with `item`, or stand alone.

The §3.1 per-facet rule is the default. These operators consume, create, or
replace facets and are the exceptions:

| Form | Facet behavior |
|---|---|
| `+` `-` | item with equal units; machine with same machine/config; solved process with same extent kind; belt with same cap; rate/capacity with same medium; config `+` merges and `-` drops; recipe drops |
| `*` `/` | item monomials; dimensionless scalar scaling; machine count; process scaling/time; integer config scaling under `*` only; belt count; rate/capacity amounts; recipe drops; under `/` a config facet is dropped |
| juxtaposition | §4.2 rules 1–5 |
| `with` | machine + config -> machine value, recipe dropped |
| `making` | machine + recipe -> process-only |
| `in` | pure quantity + uncounted machine or unsolved process -> process-only |
| `:stack-size:` | belt + rate, or pure item -> §4.7 |

Facet-specific details and error conditions are in §3.2–§3.8 and §4.

### 3.2 Item facet

The item facet is a monomial with integer exponents:

- item prototypes
- fluid prototypes
- `second`
- `joule`
- `craft`

It uses strict unit algebra. `watt` is `joule/second`. Addition and subtraction
require identical units. Multiplication and division add/subtract exponents.
Powers require integer exponents when units are present. `craft` is a real base
unit and does not convert to items.

Exponent domain:

- A dimensionless scalar base and exponent use `f64::powf` directly. There are
  no `0 ^ 0`, negative-base, or negative-exponent special cases; NaN and
  infinity results are allowed.
- A unit-bearing base requires an exact integer exponent. Negative integers are
  allowed; the coefficient uses `powf`.
- A unit-bearing exponent is an error (`DimensionalExponent`). Other facets on
  the exponent are ignored; only its item facet is read.

A **pure item/fluid quantity** has exactly one item or fluid unit at exponent 1
and no other base units. A **rate quantity** adds exactly `second^-1` and no
other units. A craft quantity has one `craft` unit and optionally `second^-1`.

### 3.3 Recipe facet

The recipe facet is a recipe reference, not a quantity. A prototype token gets
it when the entry has a recipe with the same id (for example `:iron-gear-wheel:`
has the `iron-gear-wheel` recipe).

Rules:

- **Any operation except `making` drops the recipe facet.** Arithmetic,
  property access, belt application, `in`, and `with` discard it. Quantity
  literals also drop it via scaling (§4.2). Parentheses and variable lookup are
  not operations. Belt-mode `:stack-size:` is the one exception; it retains the
  operand's components (§4.7).
- `making` consumes the right operand's recipe facet. Thus
  `m making :iron-gear-wheel:` works, but `m making (2 * :iron-gear-wheel:)` has
  no recipe and errors.
- `.recipe` returns the process's single recipe, never a value's recipe facet.
- With no `making`, `in` resolves a recipe from the machine and the selected
  unit; it does not use an operand's recipe facet.

### 3.4 Machine facet

A machine facet contains:

- the machine prototype
- its modules and beacon groups, individually, so more can be added with `with`
- an optional machine count

The optional count records whether an explicit machine quantity was attached:
`None` means an uncounted machine specification (assume one machine for display
and stats); `Some(n)` means a count was attached by scaling or machine
arithmetic.

A machine prototype is an item whose entity declares non-empty
`crafting_categories` or `resource_categories` (mining drills).

Rules:

- A prototype token for a machine item has an item facet and a machine facet,
  plus its recipe facet when the entry has a same-id recipe. Its machine count
  starts as `None`.
- `with` merges config into a machine facet and drops item, recipe, and other
  non-machine facets. The machine keeps its individual modules and beacons and
  its optional count.
- `making` consumes a machine facet and produces a process facet. It does not
  accept a process value.
- A machine facet is not a process. `in` consumes a machine facet and produces
  a separate process facet.
- Adding or subtracting machine facets requires the same machine and config.
  Otherwise the machine facet is dropped. Counts combine, treating `None` as
  one; the result has a concrete count.
- Scaling by a unitless scalar attaches or scales the count, even when the
  scalar is `1`. Division by a unitless scalar does the same: an uncounted
  machine becomes `Some(1/s)`, and a counted machine becomes `Some(n/s)`. The
  per-machine module and beacon configuration is not scaled. Multiplication by
  a unit-bearing value drops the machine facet. Unary `-` negates the count and
  leaves the config fixed.
- `.power` is the total active power for the assumed count (`None` means one),
  derived from the machine's `energy_usage` and its module/beacon consumption
  effects.
- `.machines`, `.speed`, `.productivity`, `.pollution`, and `.slots` are
  machine properties.

### 3.5 Process facet

A process facet is a production process. It stores effects, not the individual
modules or beacons that produced them:

```
Process {
    extent: Option<Extent>,         // None = unsolved template
    net: BTreeMap<BaseUnit, f64>,   // rates for unsolved/Machines, totals for MachineSeconds
    power_w: Option<f64>,           // power for unsolved/Machines
    energy_j: Option<f64>,          // energy for MachineSeconds
    recipes: BTreeSet<RecipeId>,    // for display and .recipe
}
```

```
Extent = Machines(f64) | MachineSeconds(f64)
```

- Unsolved process: `net` and `power_w` are for one machine; `energy_j` is
  absent.
- `Machines(n)`: `net` and `power_w` are totals for `n` machines.
- `MachineSeconds(tau)`: `net` and `energy_j` are totals for `tau`
  machine-seconds; `power_w` is absent.
- `making` on a counted machine multiplies per-machine `net`/`power_w` by the
  count. On an uncounted machine it leaves them per one machine.
- `in` rate → `Machines(m)`: multiply per-machine `net` rates and `power_w` by
  `m`; `energy_j` is absent.
- `in` amount → `MachineSeconds(t)`: multiply per-machine `net` by `t`, set
  `energy_j = power_w * t`, and leave `power_w` absent.
- Zero and negative counts/times are allowed algebraically; `.abs` gives
  magnitudes.

A process with `extent: None` is **unsolved**. Display and statistics assume one
machine for it. A process produced by `making` on a counted machine, by scaling
an unsolved process, or by `in` has a concrete extent.

A process is produced by `making` and `in`. It has no machine facet, so `with`
and `making` reject it. It cannot coexist with item or machine facets.

Rules:

- `making` on a machine with no count produces an unsolved process; on a machine
  with a count it produces a solved process with `Machines(n)`.
- `Process + Process` and `Process - Process` require both operands to be
  solved with the same extent kind. They add or subtract `net`,
  `power_w`/`energy_j`, and the extent magnitude. `+` unions the recipe set;
  `-` keeps a recipe only when both operands have the same single recipe,
  otherwise the recipe set becomes empty. Unsolved processes do not combine.
- Scaling a solved process by a unitless scalar scales the extent, `net`, and
  `power_w`/`energy_j`. Unary `-` negates the extent and effects.
- Scaling an unsolved process by a unitless scalar `s`, including `1`, solves it
  as `Machines(s)`: multiply `net` and `power_w` by `s` and set the extent.
  Division by a unitless scalar solves it the same way with `1/s`. Unary `-`
  solves an unsolved process as `Machines(-1)`, matching `(-m) making r`.
- A **time** operand is exactly one `second` unit at exponent 1 and no other
  units. `Machines * 2 J`, `Machines * 2 second^2`, and `MachineSeconds * time`
  are errors. `Machines * 2` scales the machine count; `Machines * 2 s` converts
  to machine time.
- `Machines * time -> MachineSeconds`: multiply `net` rates by the time, set
  `energy_j = power_w * time`, clear `power_w`, and set `tau = n * time`.
- An unsolved process `* time` assumes one machine and produces
  `MachineSeconds(time)`; its `net` rates become totals and `energy_j` is
  `power_w * time`.
- `MachineSeconds / time -> Machines`: divide `net` totals by the time, set
  `power_w = energy_j / time`, clear `energy_j`, and set `n = tau / time`.
  `Machines / time` and unsolved `/ time` are errors.
- `MachineSeconds / 0 s` follows scalar division and yields `inf`/`NaN`.
- Adding solved processes with different recipes is allowed; `.recipe` is then
  an error.
- An unsolved process is valid as the right operand of `in`; a solved process is
  not.
- `.machines`, `.time`, `.crafts`, `.power`, `.energy`, and specific unit
  selectors (`.:<item>:`/`.:<fluid>:`) are process properties. On an unsolved
  process, `.machines` is 1, `.power` is power for one machine, `.crafts` and
  unit selectors are rates, and `.time`/`.energy` are errors.
- A process has no item facet. Its output is the existing process summary: net
  rows, machine count or machine time, craft, and power or energy.
- `with` and `making` on a process are errors, not silent drops.

### 3.6 Config facet

The config facet holds per-machine modules and beacon groups:

```
Config {
    modules: [(ModuleId, u32)],
    beacons: [BeaconGroup],
}
BeaconGroup { beacon: BeaconId, count: u32, modules: [(ModuleId, u32)] }
```

Module and beacon tokens have both item and config facets. This lets them be
used as production items (`3 :speed-module-3:/s in ...`) and as configuration
values (`m with sm`).

- Config counts are nonnegative integers when present. Zero terms are elided; an
  all-zero config facet remains present but empty.
- A `:beacon:` token has item 1 and one beacon group with count 1 and no
  modules.
- Scaling a module or beacon token scales its item coefficient and its config
  counts. Adding two beacon tokens merges their beacon groups.
- A beacon group is `{ beacon, count, modules }`. Configs are canonical: module
  counts are sorted by module id, and beacon groups are sorted by beacon id then
  module set. Equality is order-insensitive.
- A config may contain only one beacon prototype. Adding beacon groups of
  different prototypes is an error.
- `+` adds module counts by id and adds beacon-group counts for the same
  beacon and module set; groups with different modules remain separate.
- Scaling by a **nonnegative integer** unitless scalar multiplies top-level
  module counts and beacon-group counts; zero terms are elided. A fractional or
  negative scalar drops the config facet instead. Module counts inside a
  beacon group are per-beacon and do not scale.
  `0.5 * :speed-module-3: / s` therefore yields a speed-module item rate with
  no config facet.
- Division never divides a config facet; the config facet is dropped and the
  other facets continue. If no facet survives, the whole operation errors.
  Configs are scaled only by `*` and are never divided.
- A scalar is a nonnegative integer when it is finite, nonnegative, and has no
  fractional part; `1.0` counts. Scaling by zero empties the config counts.
- Multiplication by anything else (a unit-bearing value, another config, time)
  drops the config facet.
- `-` drops the config facet. Beacon groups and modules are additions, not
  signed quantities.
- Write `Cb` for a config with exactly one beacon group, `Cm` for a
  module-only config, and `C` for a general config. Config juxtaposition is
  partial:
  - `Cb Cm -> Cb`: the left config has exactly one beacon group and the right
    config has only modules. The right modules attach to that one beacon group;
    the right item facet is consumed and the left item facet (if any) remains.
  - `Cm Cm -> Cm`: both configs have only modules. Their module lists combine;
    both item facets are consumed and the result is config-only.
  - Any other config juxtaposition (`Cb Cb`, `Cm Cb`, or a left config with
    more than one beacon group) is an error. `bc sm` attaches; `sm bc` errors.
  - Where defined, config juxtaposition is associative; `Cm Cm` is commutative,
    `Cb Cm` is not.
- `+` never modifies a beacon group: it combines the non-beacon module lists
  and combines beacon-group lists. It never attaches modules to a beacon; only
  juxtaposition attaches (`Cb Cm`).
- `with` merges a config value into a machine facet and returns a machine
  value with the recipe facet dropped.
- Config counts are per machine when merged.
- Beacon slots/effects are validated when the group is constructed
  (juxtaposition). Machine module slots/effects are validated by `with`.
  Recipe-dependent productivity gating is validated by `making`/`in`.
- `with` rejects invalid slots/effects and over-capacity configurations.

### 3.7 Belt facet

The belt facet records how many belt tiles a value represents and the stacking
cap those tiles use:

```
Belt { count: f64, cap: Cap }
```

Rules:

- A belt token has item + belt + rate: belt count 1, cap `Limit(1)`, and one
  rate term with the same cap.
- Scaling by a unitless scalar keeps the belt facet and scales its count; the
  cap is unchanged.
- Addition/subtraction keeps the belt facet only when both operands have a belt
  facet and the same cap. Counts add or subtract; the cap is retained. Belt
  tiers need not match: throughput and capacity depend on counts and cap, not
  tier.
- `:stack-size:` in belt mode keeps the belt, rate, and recipe facets and sets
  both caps to the belt stacking level. If the operand has an item facet, the
  prefix multiplies its coefficient by the belt item's stack size; if it has no
  item facet, the result keeps no item facet. Any other facet is dropped. Zero
  rate terms do not remove the belt cap. A present item with no stack size is
  an error.
- Most other operations drop the belt facet (time arithmetic, `in`, `with`,
  `making`, applying the belt to an item).
- `.capacity` on a value with a belt facet derives
  `8 slots/tile * belt count`, with `max_stack = belt.cap`.
- A value with no belt facet and no native capacity facet has no `.capacity`.

Belt stacking level is a research/setting value. The display-only "stacked
belts" toggle does not affect evaluation.

### 3.8 Rate and capacity facets

A rate or capacity facet has a medium: item or fluid.

**Item rate** is a map from stack cap to stacks per second:

```
Rate::Items { terms: BTreeMap<Cap, f64> }   // stacks/s
```

**Item capacity** is a map from stack cap to stack slots:

```
Capacity::Items { terms: BTreeMap<Cap, f64> }
```

**Fluid rate** is a volume per second; **fluid capacity** is a volume. They have
no stack caps.

```
Cap = Full | Limit(u32)
```

- `Full` means the item's own stack size.
- `Limit(n)` means at most `n` items per stack.
- `Limit(1)` is an ordinary one-item stack.
- Caps are non-negative integers. `Full` and `Limit(n)` are distinct keys even
  when they happen to be equal for a particular item.
- Zero terms are removed from the map, but the facet remains present. `r - r`
  is a zero rate, not an absent rate.
- Addition/subtraction merges terms by cap. Cap sets need not match. Item
  medium must match; fluid medium must match. Different media drop the facet.
- Scaling scales every amount.
- Applying an item rate to an item evaluates
  `rhs_item_coef * Σ amount * min(cap, item_stack_size)`, with `Full` using the
  item stack size, and yields an item rate (a quantity with `second^-1`).
  Applying an item capacity to an item evaluates the same sum and yields an
  item amount. The rate facet's amounts already carry scaling of the
  rate-bearing value; the coefficient is the right operand's item quantity.
  Applying a fluid rate/capacity to a fluid uses `rhs_fluid_coef * volume rate`;
  a fluid rate yields a fluid rate and a fluid capacity yields a fluid amount.
  Thus `b (3 :iron-plate:)` is three times the one-item rate. The applied
  operand must be a pure item/fluid quantity; its other facets are dropped by
  the application.
- Item vs fluid medium mismatch is an error when applying.

A rate or capacity value is **isolated** when rate or capacity is its only
facet, which is what `.rate` and `.capacity` return.

A plain item rate such as `3 :iron-plate:/s` is an item-facet quantity, not a
rate facet. `.rate` on it is an error. Rate facets come from belt/inserter
tokens and from `capacity / time`; a Full term is reachable as, for example,
`:steel-chest:.capacity / 1 s`. Plain item rates and rate facets do not mix in
arithmetic.

- `rate * time -> capacity` and `capacity / time -> rate` are defined only for
  isolated values. The conversion replaces the rate facet with the capacity
  facet (or vice versa) and drops every other facet; the result keeps medium and
  caps. On a non-isolated value the rate/capacity facet is dropped by §3.1
  instead.
- Division of isolated rate/capacity values is defined only when both have the
  same medium and, for items, exactly one term with the same cap. Multi-term
  item rates and capacities cannot be divided. Fluid values have no caps, so
  only the medium must match.
  - `rate / rate ->` dimensionless item scalar;
  - `capacity / capacity ->` dimensionless item scalar;
  - `rate / capacity ->` item scalar with `second^-1`;
  - `capacity / rate ->` item scalar with `second`.
  Incompatible cap sets or media are errors for these isolated divisions, not
  facet drops. An empty divisor map is a zero rate/capacity: if the dividend is
  single-term, the result is `inf`/`NaN` and no cap match is required.
  Multi-term dividends still error. Non-empty divisors require exactly one term
  with the same cap.

Rate facets are constructed from belt/inserter tokens or by dividing capacity:

```
:transport-belt:.rate          # 15/s (Limit 1)
:steel-chest:.capacity / 1 s   # 48:stack-size:/s (Full)
```

Display order is `Full` first, then `Limit` in descending order. The notation
below is output-only and is not input syntax:

- `Full` -> `:stack-size:`
- `Limit(4)` -> `:stack-size:₄`
- `Limit(2)` -> `:stack-size:₂`
- `Limit(1)` -> no icon or subscript

Examples:

```
30:stack-size:/s + 15:stack-size:₄/s + 10/s
30:stack-size: + 15:stack-size:₄ + 10
```

Subscripts are available in every installed monospace chain (possibly via the
bundled fallback font), so no tofu fallback is required. Some primary faces
lack them natively and borrow a narrower fallback glyph; if grid alignment
becomes a problem, detect this from the primary face's cmap, not from
`has_glyph`.

Fluid rate/capacity display uses the volume units directly (`fluid/s`,
`fluid`) and does not use stack-size notation.

### 3.9 Machine modifiers and coefficients

For a machine and its allowed module/beacon effects:

```
speed          = machine.speed * (1 + Σ speed effects)
productivity   = machine.base_productivity
               + Σ productivity module effects (if recipe allows)
               + research productivity
consumption    = 1 + Σ consumption effects
power_w        = energy_usage_w * consumption
pollution/min  = base_pollution * consumption * (1 + Σ pollution effects)
```

Sums include machine modules and beacon modules; a beacon module contributes
`effect * transmission` (§6), scaled by its count and beacon-group count. The
machine's `allowed_effects` filter both its own modules and beacon-transmitted
effects; a beacon's `allowed_effects` filter which modules may be placed in it.
Productivity modules require `recipe.allow_productivity == true`; built-in and
research productivity do not. Beacon power is excluded.

For recipe `R`, selected unit `u`, per machine-second:

```
S = speed
T = R.craft_time
A_prod(u) = Σ expected product amounts for u per craft
A_ing(u)  = Σ ingredient amounts for u per craft
A_ign(u)  = Σ ignored_by_productivity parts of product amounts for u
P = productivity

products(u)    = (S/T) * (A_prod(u) + P * (A_prod(u) - A_ign(u)))
ingredients(u) = (S/T) * A_ing(u)
k(u)           = products(u) - ingredients(u)
k(craft)       = S/T
```

`A` is an amount per craft. Repeated product or ingredient entries for the same
unit are summed. If `u` appears on both sides, the terms net.
`facet_machine.rs` is normative for the machine/module arithmetic; beacon
contributions are specified here.

## 4. Syntax

### 4.1 Effective precedence

Tightest first:

1. property access `.`
2. juxtaposition
3. `^`
4. unary `-`
5. `*` `/`
6. `+` `-`
7. `in`

`with` and `making` are operand-level **machine-expression** forms, not infix
operators:

```
MachineExpr := Primary ('with' ConfigExpr)* ('making' Operand)?
Operand      := Primary
```

`Primary` is a quantity literal, prototype token, variable, parenthesized
expression, or a property access on one. Juxtaposition, arithmetic, and `in`
are outside `MachineExpr`. This makes `3 :foundry: making r` a machine
expression, while `m making r * 2` leaves the `* 2` outside.

`^` is right-associative. Unary minus binds looser than `^`.

Special parse modes:

- `making` attaches after the complete `with` chain and before surrounding
  arithmetic. Its right side is one `Primary` value. Thus
  `m with sm making r` is `(m with sm) making r`,
  `2 * m making r` is `2 * (m making r)`, and
  `m making r * 2` is `(m making r) * 2`. It does not attach to a
  juxtaposition or arithmetic result; parenthesize such an expression, as in
  `(m1 + m2) making r`.
- `with` takes a **config expression** on the right: it accepts juxtaposition,
  `.`, `^`, unary, `*`, `/`, `+`, `-`, and parentheses, but stops at `making`,
  `with`, `in`, `)`, and `#`. The left side is the machine expression built so
  far.
- `in` takes a **process expression** on the right: it accepts `MachineExpr`
  (therefore `with` and `making`), but stops at arithmetic and `in`. Therefore
  `q in m * 2` parses as `(q in m) * 2`; write `q in (m * 2)` to apply the
  arithmetic to the machine.
- `:stack-size:` is a prefix taking one **Primary**. A quantity literal
  (`3 :iron-plate:`) counts as one Primary. It consumes no further
  juxtaposition; it stops at unary `-`, `^`, `making`, `with`, `in`, and
  arithmetic. It binds tighter than juxtaposition, `^`, and `*`. Thus
  `:stack-size: 3 :iron-plate:/s` is `(:stack-size: 3 :iron-plate:)/s`,
  `:stack-size: b1 :iron-plate:` is `(:stack-size: b1) :iron-plate:`,
  `:stack-size: b1 ^ 2` is `(:stack-size: b1) ^ 2`, and `:stack-size: -b1`
  requires `:stack-size: (-b1)`.

Examples:

```
:stack-size: 3 :iron-plate:/s   # (:stack-size: 3 :iron-plate:)/s
:stack-size: b1 :iron-plate:    # (:stack-size: b1) :iron-plate:
:stack-size: b1 ^ 2             # (:stack-size: b1) ^ 2
:stack-size: -b1                # error; use :stack-size: (-b1)
:stack-size: (b1 :iron-plate:)  # error: applies the belt before stacking
```

Why these rules:

- Unary `-` negates item, machine count, process, belt, rate, and capacity
  quantities. A machine's per-machine config is fixed; an uncounted machine
  becomes `Some(-1)`. A separate config facet is dropped, so a config-only
  value errors. Binary `-` is defined for the same list; config `-` drops the
  config facet; recipe never subtracts. `^` applies only to item/scalar facets;
  other facets drop. Division by zero follows scalar semantics;
  `Machines / time` and unsolved `/ time` are errors; a config facet drops
  under `/` and only survives as an error if nothing else remains.
- `with` takes a config expression on its right, so a config sum groups without
  parentheses: `m with sm + bc` is `m with (sm + bc)`.
- The right of `with` is a config expression that stops at `making`, so
  `m with sm making r` is `(m with sm) making r`, not `m with (sm making r)`.
- `making` is part of `MachineExpr`, so it attaches after the `with` chain and
  before surrounding arithmetic: `m making r + x` is `(m making r) + x`, and
  `2 * m making r` is `2 * (m making r)`. Its right side is one `Primary`, so
  `m making r * 2` is `(m making r) * 2`.
- `in` stops at arithmetic, so `q in m * 2` is `(q in m) * 2`; it does include
  `with`/`making`, so `q in m making r` is `q in (m making r)`.
- `with` is left-associative and may be repeated:
  `m with sm with bc` is `(m with sm) with bc`.

### 4.2 Juxtaposition

A number immediately followed by a unit token or prototype token is a single
quantity literal. Remaining juxtaposition is left-associative. Two juxtaposed
scalars multiply.

Literal construction applies the dimensionless-scalar scaling rules to the
token: multiply every quantitative facet it has (item coefficient, belt count,
rate/capacity amounts, and config counts) by the number; if the token has a
machine facet, set its count to `Some(n)`; drop the recipe facet. Config counts
follow §3.6: a fractional literal drops the config facet. Thus `3 :foundry:`
has count `Some(3)` and no recipe, and `3 * :foundry:` behaves the same. Use the
bare token (`:iron-gear-wheel:`) when a recipe facet is needed.

Juxtaposition is a binary operator. Its behavior depends on the left facets:

1. LHS has a rate facet and RHS is an item/fluid quantity:
   apply the rate to the RHS (item or fluid), producing a rate quantity.
2. LHS has a capacity facet and RHS is an item/fluid quantity:
   apply the capacity, producing an amount.
3. LHS and RHS both have a config facet:
   - `Cb Cm`: LHS has exactly one beacon group, RHS is module-only. Attach the
     RHS modules to that group; RHS item consumed, LHS item retained.
   - `Cm Cm`: both are module-only. Combine module lists; consume both item
     facets and return config-only.
   - Any other config shape is an error.
4. Otherwise, if either operand is a dimensionless scalar, scale every scalable
   facet of the other value, including its item facet. Config follows §3.6:
   only a nonnegative integer scalar scales it; otherwise config drops.
   `:foundry: 2` and `2 :foundry:` both give two machines and both drop the
   recipe facet; `2 :foundry: making r` works because `r` supplies the recipe.
5. Otherwise, error.

Juxtaposition multiplies only through rule 4: one side must be a dimensionless
scalar. Two unit-bearing values, including two item-bearing values or two time
values, require explicit `*`.

A pure item/fluid quantity in rules 1 and 2 means an item facet with exactly one
item or fluid unit at exponent 1 and no other units. “Pure” describes the units,
not the facet set; other facets are dropped by the application.

Belt application uses the rate facet; the belt facet itself is dropped.

### 4.3 Property access

`value . selector` is postfix and binds tighter than juxtaposition. Selectors are
property words, prototype/unit tokens (`.:iron-plate:`), or signals
(`.:stack-size:`, `.:lightning:`).

In tables, `.:item:`/`.:fluid:` are placeholders for `.:<prototype>:`. The
actual selector is a specific token, for example `.:iron-plate:`. The generic
item/fluid signal icons are not language values.

### 4.4 `with`

`m with cfg` requires `m` to have a machine facet and `cfg` to have a config
facet. It returns a machine value with the config merged, dropping item, recipe,
and other non-machine facets. `with` is left-associative and can be repeated:

```
m with sm with bc
```

`with` keeps the machine's optional count and merges modules/beacons into the
machine's individual configuration. It is not a process operator: configure the
machine before `making`, because a process stores only baked effects.

### 4.5 `making`

`m making r` requires:

- `m`: machine facet;
- `r`: a value with a recipe facet.

The recipe facet of `m`, if present, is ignored and dropped; `r` supplies the
recipe. Other facets on `r` are ignored and dropped.

It returns a process-only value. If the machine count is `None`, the process is
unsolved and assumes one machine for display/stats. If the count is `Some(n)`,
the process is solved as `Machines(n)`.

`making` validates that the machine can craft the recipe (category intersection,
including `resource_categories` for drills) and that productivity modules in the
machine or its beacons are legal. Productivity modules are rejected when
`recipe.allow_productivity` is false, i.e. they are legal only when it is true.
Slot and allowed-effect validation happened earlier in `with`/construction.

| Phase | Checks |
|---|---|
| beacon group construction | beacon module slots and beacon allowed effects |
| `with` | machine module slots and machine allowed effects; beacon group validity |
| `making` / auto-resolved `in` | recipe category; productivity gating for machine and beacon modules |

`making` is not allowed on a process value. A machine count attached by scaling,
including `1`, therefore changes the result from an unsolved to a solved
process:

```
:foundry: making :casting-iron:     # unsolved; displays one machine
3 :foundry: making :casting-iron:   # solved Machines(3)
1 :foundry: making :casting-iron:   # solved Machines(1)
```

### 4.6 `in`

`q in m` requires:

- `q`: a pure item/fluid amount, a pure item/fluid rate, or a craft amount/rate;
- `m`: either a machine facet with **no attached count** (`count == None`), or
  an unsolved process (`extent == None`) with exactly one recipe.

A machine with a count, even `1`, is an error. So is a solved process. Validity
depends on whether a count/extent was attached, not on a floating-point
comparison:

```
:iron-plate: in :foundry:                          # allowed
:iron-plate: in (1 :foundry:)                      # error: count attached
:iron-plate: in (0.5 * 2 * :foundry:)              # error: count attached
:iron-plate: in (:foundry: making :casting-iron:)  # allowed: unsolved process
:iron-plate: in (1 * (:foundry: making :casting-iron:))  # error: solved
```

A process is not a machine, so `x in (y in :foundry:)` is an error.

Recipe selection:

1. the recipe of the unsolved process on the right;
2. otherwise auto-resolve: a recipe the machine can craft (category intersection,
   including `resource_categories` for drills) whose products include the
   selected unit with positive expected amount. Candidates are also filtered by
   recipe productivity gating when the machine or its beacons carry productivity
   modules;
3. the registry recipe whose id equals the left operand's single item/fluid
   prototype id may be used only as a tiebreaker when it is one of those
   machine-compatible candidates. The left value's recipe facet is still
   ignored;
4. zero candidates or still-multiple candidates is an error. `craft` quantities
   require an explicit recipe. An unsolved process with exactly one recipe is
   explicit; a bare machine is not. Thus `1 craft in (m making r)` is valid,
   while `1 craft in m` errors.

After auto-resolution, `in` performs the same category and productivity
validation as `making`.

“Pure” describes the units of the item facet, not the facet set. Extra facets
on `q` (recipe, machine, process, config, belt, rate, capacity) are ignored and
dropped. A rate means an item monomial with `second^-1`, not a separate rate
facet; a standalone rate or capacity facet with no item facet is not a
quantity. Thus `:speed-module-3: in m` is valid (the config is ignored), and
`:transport-belt: in m` is not a rate use of the belt. An explicit recipe may
involve the selected unit as a product or an ingredient, but `k(unit) == 0` is
an error.

The result is a solved process. Let `k(unit)` be the recipe's net coefficient
for the selected unit per machine-second.

- item/fluid: `magnitude = q.coef / |k(unit)|`; craft:
  `magnitude = q.coef / k(craft)`;
- a rate (`second^-1`) gives `Machines(magnitude)`, with `net` rates and
  `power_w` scaled by magnitude;
- an amount gives `MachineSeconds(magnitude)`, with `net` totals scaled by
  magnitude and `energy_j = power_w * magnitude`;
- the sign of the quantity is kept. For example, with a recipe that nets one
  plate per machine-second, `3 :iron-plate: in m` is three machine-seconds.

### 4.7 `:stack-size:` prefix

The prefix has two modes.

**Belt mode.** If the operand has a belt facet, the prefix keeps the belt, rate,
and recipe facets, sets the belt cap and any rate-term cap to
`Limit(level.clamp(1, 4))` for the current belt stacking level, and drops any
other facet. If the operand has an item facet, the prefix multiplies its
coefficient by the belt item's stack size; without an item facet, the result
has no item facet. A present item with no stack size is an error. Belt facet
addition already guarantees exactly one cap, so this is always well-defined.

A belt token's rate is unstacked by default: one `Limit(1)` term. The prefix
produces the stacked form.

**Item mode.** If the operand has no belt facet, its item facet must be a pure
item quantity. “Pure” describes the item units; extra facets are allowed and
dropped. The prefix returns an item-only value whose coefficient is the
operand's item coefficient multiplied by that item's stack size. An operand
with no item facet, an item with no `stack_size`, and every fluid, is an error.
Use `(:stack-size: 3 :iron-plate:)/s` for a rate.

```
:stack-size: :iron-ore:        # 50 iron-ore, for a 50-item stack
:stack-size: 3 :iron-ore:      # 150 iron-ore
:stack-size: :transport-belt:  # 100 transport-belt, 1 belt, stacked rate
:stack-size: b1 :iron-plate:   # stacked belt applied to iron plates
```

Belt mode takes priority: `:stack-size: :transport-belt:` stacks the belt and
also scales its item coefficient to 100; it does not use item mode.

## 5. Properties

A property selects the facet it reads, drops the other facets, and returns a
scalar or facet-only value. Absence or ambiguity is an error, except where noted.

| Property | Reads | Result |
|---|---|---|
| `.rate` | rate facet | rate-only value |
| `.capacity` | capacity facet; or belt facet + belt cap | capacity-only value |
| `.stack-size` | pure item quantity | prototype stack size; coefficient ignored |
| `.power` | machine/process count, config with beacons, or item/equipment entity | watts |
| `.energy` | solved process `MachineSeconds`, or pure item/equipment stored energy | joules |
| `.electric` / `.:lightning:` | machine/process by extent; config beacons; item by unique power/energy | power or energy |
| `.machines` | machine (uncounted means one), solved process `Machines`, or unsolved process | machine count |
| `.time` | solved process `MachineSeconds` | seconds |
| `.crafts` | process | `craft/s` or `craft` |
| `.speed`, `.productivity`/`.prod`, `.pollution`, `.slots` | machine | per-machine derived scalar; `.slots` is module-slot capacity |
| `.recipe` | process with one recipe | recipe-only value |
| `.:<item>:` / `.:<fluid>:` | process | signed net row; zero if absent |
| `.abs` | all quantitative facets | absolute values; recipe facet dropped |

Rules:

- `.rate` reads a rate facet; a plain item rate such as `3 :iron-plate:/s` has
  no rate facet and errors.
- `.power` on a machine/process count is the total for that count:
  `(2 :beacon:).power == 2 :beacon:.power`. An uncounted machine and an
  unsolved process assume one machine.
- `.power` on a config facet with beacon groups is
  `Σ group.count × beacon.energy_usage`; machine-module config without beacons
  has no `.power`. When an item facet is present, item power takes priority;
  config-beacon power applies only to config-only values.
- `.power` reads powered item entities and equipment (`energy_usage`,
  `energy_consumption`, `power`), not just crafting machines. `.energy` reads
  stored energy (`buffer_capacity`, `max_energy`). Both require a pure item
  quantity and scale by its coefficient. Flow limits are ignored.
- `.stack-size` requires a pure item quantity and returns the prototype stack
  size, ignoring the coefficient: `(3 :iron-plate:).stack-size` is 100.
  `3 :iron-plate:/s` is an error. The `:stack-size:` prefix instead multiplies
  the quantity by the stack size.
- `.speed`, `.productivity`, `.pollution`, and `.slots` are per-machine values;
  `.slots` is the machine's `module_slots` capacity. `.power` is total for the
  count. `.machines` on `MachineSeconds` is an error.
- `.productivity`/`.prod` on a machine without a recipe uses base productivity
  plus productivity modules (treated as allowed); research productivity
  requires a recipe.
- `.power` is strict for machine counts and solved `Machines`; `.energy` is
  strict for solved `MachineSeconds`. An unsolved process has no time extent, so
  `.time` and `.energy` are errors.
- On an item/equipment entity, `.electric`/`.:lightning:` returns power when
  only power is defined, energy when only stored energy is defined, and errors
  when both are defined. On a config with beacons it returns power.
- `.recipe` is process-only; machines have no recipe.
- `.abs` applies to item coefficients, machine counts, belt counts, config
  counts, process extents, process net rows/power/energy, and every rate and
  capacity amount. An uncounted machine or unsolved process keeps its absent
  count/extent. It drops the separate recipe facet. If no quantitative facet
  exists, it errors.
- Specific unit selectors (`.:<item>:` / `.:<fluid>:`) are process-only; an
  absent net row projects to zero.

Beacon power is not included in a process's power; add `:beacon:.power`
explicitly. The same applies to other external power draws.

## 6. Beacons

Beacon data: `module_slots`, `allowed_effects`, `distribution_effectivity`,
`profile`, and `energy_usage`.

The total number of beacons affecting the machine is `n`; the profile
contributes `profile[n - 1]` (clamped to the profile length). If `n = 0`, there
is no beacon effect. Beacon counts are nonnegative integers when present;
fractional or negative scaling drops the config facet (§3.6), so `n` is an
integer.

```
total_effect = profile[n - 1]
             * sum over beacons of (
                   distribution_effectivity_i
                   * sum of module effects in beacon i
               )
```

Always use the general sum above; there is no simplified per-group or
identical-beacon form.

All beacon groups in a config must use the same beacon prototype (§3.6).
Adding groups of different beacon prototypes is an error, so the `profile`
used by `profile[n - 1]` is unambiguous.

Beacon groups exist only as a calculator convenience; they do not change the
formula. Sum each group's per-beacon module effects and use the total `n` only
in `profile[n - 1]`.

- Beacon counts are per machine.
- Beacon modules validate against the beacon's slots and allowed effects.
- Beacon module effects apply to the machine's speed, consumption, and
  pollution. Beacon power is excluded from process power.
- `.power` on `:beacon:` or a beacon config value reports its own energy usage.
- Beacons do not benefit from their own modules.
- Quality is not modelled.

Syntax:

```
3 :foundry: with 2 :speed-module-3: with 4 :beacon: 2 :speed-module-3: making :casting-iron-gear-wheel:
```

or, with config values:

```
sm = 2 :speed-module-3:
bc = 4 :beacon: 2 :speed-module-3:
m with (sm + bc)
```

## 7. Data

### 7.1 Belts

- Base slot rates are data-derived: `belt_speed × 60 × 8` slots/s, where
  `belt_speed` is the belt entity's speed. Vanilla values are yellow 15, red 30,
  blue 45, green 60. These are `stacks_per_second`; at `Limit(1)` they are also
  items/s. Items/s is `rate * min(cap, item stack size)`.
- A belt token is any item whose entity is a transport belt.
- Belt token default: item + belt + rate `{Limit(1): base}`.
- Capacity: 8 slots per tile, a hardcoded engine constant.
- Stacking level: research/setting.

### 7.2 Inserters

- `hand_size` is cosmetic and is not the cap.
- Effective capacity is an integer item count, tested in this order:
  - stack inserter (`stack_size_bonus > 0`):
    `2 + stack_size_bonus + bulk-inserter-capacity-bonus`;
  - bulk (`bulk` flag): `2 + bulk-inserter-capacity-bonus`;
  - non-bulk: `1 + inserter-stack-size-bonus`.

  `stack_size_bonus` here is the prototype field; the other two names are
  research effects. The stack inserter also has the `bulk` flag, so testing
  `bulk` first would omit its +4 and understate throughput.
- Throughput is derived from `rotation_speed` with tick quantisation:

```
ticks_half = ceil(0.5 / rotation_speed) - 1
cycle_ticks = 2 * ticks_half
cycles_per_second = 60 / cycle_ticks
items_per_second = capacity * cycles_per_second
```

  Requires `0 < rotation_speed < 0.5`; otherwise the formula is an error.
  Extension is ignored for all inserters; the formula uses rotation only. This
  formula reproduces the published chest-to-chest rates for every vanilla
  inserter and capacity level. Bulk inserters are those with the `bulk` flag;
  the stack inserter is identified by `stack_size_bonus`. All inserters are
  assumed to move 180° at machine-to-machine distances, including modded
  inserters.
- Inserter rate: item medium, one `Limit(capacity): cycles_per_second` term.
  The limit is clamped by the item's stack size at application, so
  non-stackable items move one per cycle. No belt facet, no `.capacity`.

### 7.3 Containers and fluids

- Chests, cars, cargo wagons: item capacity from `inventory_size` slots, `Full`
  cap.
- Tanks and fluid wagons: fluid capacity volume.
- Pumps: fluid rate.
- Fluid rate/capacity use the fluid medium and volume units; no stack caps.
- Belt capacity is item-only.

### 7.4 Power and energy metadata

- Power: entity `energy_usage`, equipment `energy_consumption`/`power`, and
  equivalent power fields. Radar, beacons, exoskeletons, and similar entities
  are included.
- Stored energy: equipment `buffer_capacity`/`max_energy`, used by `.energy`.
- Equipment items (exoskeletons, personal batteries, shields) are ordinary
  namespace items. Post-processing joins their equipment prototype to supply
  `.power` and stored `.energy`; they have no machine facet.

## 8. Output

Facet display order:

1. item
2. rate
3. capacity
4. machine
5. process
6. config
7. recipe

- A single-line gutter result shows the first present of: item, machine,
  process, config. If none is present, fall back to rate, then capacity, then
  recipe so that rate-only and recipe-only values are not blank.
- A process facet never coexists with an item or machine facet by construction,
  so the single-line priority is unambiguous.
- The multiline result popup shows all displayable facets; `belt` is internal
  and is not displayed directly. Use `.capacity` or the accompanying rate to see
  its effects.
- Belt mode retains the item facet, so `:stack-size: :transport-belt:` follows
  the normal item priority and shows its scaled item quantity; use `.rate` or
  `.capacity` to display the belt facets.
- Display notation (stack-size terms, compact machine/config clauses, `0` for an
  empty config) is output-only and is not guaranteed to re-parse.
- A process shows the existing summary: machine count or machine time, signed
  net rows, craft, and power or energy. An unsolved process assumes one machine.
- Machine and config displays use compact construction syntax: counts are
  written directly before their tokens, clauses are joined with `+`, and one
  `with` introduces the config. Omit a count of 1.
  Examples: `:foundry: with 4:speed-module-3:+4:beacon:2:efficiency-module-2:`
  and config-only `4:speed-module-3:+4:beacon:2:efficiency-module-2:`.
  An empty config facet displays `0`.
- Recipe-only values show the recipe icon/name.
- Applied rate/capacity values collapse to a scalar item or fluid amount.
- A present but empty rate/capacity facet displays `0/s` or `0`, not an empty
  line.
- `Full`/`Limit` display follows §3.8; fluid rates/capacities use volume units.
- Numbers use the existing decimal/metric/time-settings formatting; caps are
  not formatted.

## 9. Settings and research

Evaluation-affecting:

- belt stacking level (research level)
- inserter capacity research level, saved as `inserter_capacity` with default 0
- productivity research levels

Display-only:

- time unit
- metric prefixes for items
- belt display mode for item rates
- whether belt-like display uses stacked belts
- decimal places
- font

The `:stack-size:` prefix uses the research stacking level, not the display
toggle.

## 10. Errors

Errors are reported when:

- no facet survives an operation; the message names the operation, lists the
  facets present on each operand, and states why each final facet was dropped;
- juxtaposition matches none of §4.2's dispatch rules, including two
  unit-bearing values that would need explicit `*`;
- a required facet is absent (`.rate`/`.capacity`/`.recipe`/`.machines`/...);
- a facet is ambiguous (e.g. `.stack-size` on a multi-item monomial);
- `.abs` is applied to a value with no quantitative facet;
- `^` has a unit-bearing exponent or a unit-bearing base with a non-integer
  exponent;
- a machine config, recipe, category, module, or beacon is invalid;
- `in` cannot resolve exactly one recipe, the explicit recipe does not involve
  the selected unit, or `k(unit) == 0`;
- `in` is given a machine with an attached count or a solved process;
- `making` is used on a process, or its recipe category/productivity gate is
  invalid;
- `with` has no machine facet or no config facet;
- process addition/subtraction receives an unsolved process or two different
  extent kinds;
- process time arithmetic is unsupported (`Machines / time`, unsolved `/ time`,
  `MachineSeconds * time`, or a non-time operand);
- `.power` is requested from `MachineSeconds`, or `.energy` from `Machines`;
- `.machines` is requested from `MachineSeconds`;
- `.electric` is ambiguous because an item has both power and stored energy;
- `.time` or `.energy` is requested from an unsolved process;
- `.recipe` is requested from a process with zero or multiple recipes;
- `:stack-size:` has no valid belt or item operand, or the item has no stack
  size;
- isolated rate/capacity division uses multi-term items or mismatched media/caps;
- a rate/capacity medium does not match the applied item/fluid;
- a beacon or module configuration is over capacity;
- a parse fails, a variable is unknown, or a variable is redefined.

When an operation drops facets, no warning is emitted; the details popup shows
only the facets that survived.

(r1 :iron-gear-wheel: in m1).:iron-plate:
r1 :iron-gear-wheel: in m1

3 :foundry: with 2 :speed-module-3: with 4 :beacon: 2 :speed-module-3: making :casting-iron-gear-wheel:

(2 :beacon:).power
2 :radar:.power
:accumulator:.energy

100 :transport-belt:.capacity :iron-plate:
(:transport-belt: + :fast-transport-belt:) :iron-plate:

3 :speed-module-3:/s in :electromagnetic-plant:

(:iron-plate: in :foundry:) + (:iron-gear-wheel: in :foundry:)
