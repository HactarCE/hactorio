The general structure of this app should be a text document with tabs. Each line has an output off to the side, which updates automatically. I want fuzzy autocomplete for every item/fluid/recipe in the game, so I could type `ipl` to search for "iron plate," and then if I select it it'll be inserted into the document as an icon. This can use the brand-new autocomplete popup added in egui 0.37 (`CompletionPopup`; it supports icons in the popup via `Suggestion::content`, but `Suggestion::insert` is plain text and the popup performs the replacement itself).

## Syntax

- basic arithmetic (+ - * / ^ and parens)
- comments (starting with `#`, goes to end of line)
- ad-hoc variables, which can contain units: `rate1 = 3 iron-plate / second`

Statements are explicit rather than "every line is an expression":

```
name = EXPR     # definition
EXPR            # anonymous expression; output shown
# comment
```

Variables are visible only to later lines in the same tab. There is no visibility across tabs.

`EXPR in MACHINE` is an expression, not a statement-level clause.

## Values

A value is a single monomial: a coefficient plus an integer exponent for each base unit.

```rs
struct Value {
	coef: f64,
	/// Exponent per base unit. Zero exponents are removed; iteration is sorted.
	units: BTreeMap<BaseUnit, i64>,
}
```

- `100 iron-plate / second` is one value; `3 gear / minute` is another.
- Addition and subtraction require identical units (same map); coefficients are combined.
- Multiplication adds exponents, division subtracts them, `^` multiplies them. The exponent must be an integer when the value has units.
- Adding different items is an error; there is no sum-of-different-items value.

## Units

- basic metric prefixes (k, M, G) are *parse-time and display-time only*; they are not part of the value. Typing `3 k iron-plate` produces `3000 iron-plate` (which displays as `3 k iron-plate` only if the prefix toggle is on).
- units for time (seconds, minutes, hours), convertible to each other with fixed factors
- basic electricity units (J, W), with W = J/s
- opaque base unit for every item/fluid/recipe in the game; alternate recipes have distinct IDs, so recipe choice is expressed by choosing the corresponding icon/token
- hybrid units (e.g., `item / second`, `item / item`, `machine * second`)
- `machine` (a count of machines) and `craft` (a recipe execution); both only acquire meaning in the context of a machine value

### Belt rates

Belt throughput is a literal form, not a unit:

```
2 yb iron-plate   == 30 iron-plate / second
1 gb gear         == 60 gear / second
```

`yb` / `rb` / `bb` / `gb` are 15 / 30 / 45 / 60 items per second. `syb` / `srb` / `sbb` / `sgb` are the same multiplied by the effective stack size, `min(tab stacking level, item stack size)`. The count defaults to 1. The item after the belt token must be an item, not a fluid.

Belt literals always produce a per-second rate, regardless of the tab time unit.

There are no ad-hoc unit relations and no cross-item conversion: `iron-plate` and `gear` are distinct dimensions that never convert into each other. There is no `EXPR to UNIT` syntax.

I want a reference panel on the side with stats for machines, recipes, etc. that are mentioned in the text document. Mention detection is by token; unknown/typo tokens are ignored by the panel (and should ideally be impossible to insert in the first place).

## Game data and icons

Imported on first run from the installed game; nothing is bundled or redistributed.

- locate the Factorio binary (Steam library paths, then a file picker), verify with `--version`
- run `--dump-data`, `--dump-icon-sprites`, and `--dump-prototype-locale` with the game closed; output lands in `script-output`
- post-process into a compact cache in `hactorio-data`, keyed by a hash of the dumps; the enabled mod set is included automatically
- cache and icons live in app data, never in the repo

Icons:

- one PUA codepoint per prototype (items, fluids, recipes), assigned deterministically and stored with the cache
- rendered via `Context::add_glyph_rasterizer` (highest-priority `GlyphRasterizer`) returning color glyph bitmaps; no font file needed
- the in-memory buffer holds PUA characters; saving writes plaintext prototype IDs and loading converts back
- unknown names stay literal text

## Machine syntax

A machine value denotes one or more machines with a fixed configuration running one recipe:

```
foundry 3 productivity-module-2 1 speed-module-3 3 beacon 2 efficiency-module-3 1 beacon speed-module-3 efficiency-module-3 making iron-plate
```

That example is mechanically valid: the foundry has 4 module slots (3 + 1), and the 4 beacons hold 8 modules (3x2 + 1x2); efficiency modules are legal in beacons.

Parsing: the machine spec extends to the next newline, operator, `)`, or `#`. Counts bind to the following token, and each `beacon` token starts a new beacon group; tokens after a `beacon` are that beacon's modules. `making RECIPE` is optional: without it, the expression's item must have exactly one producing recipe that the machine can craft, and that item is the recipe's product. Craft quantities (`crafts`, `crafts/s`) have no item to resolve the recipe, so they require an explicit `making RECIPE`.

### Modes

A machine value has one of two units:

- `machine` -- a count of machines (a bare machine value is 1 machine)
- `machine * second` -- an amount of machine time

For a fixed configuration, the recipe yields a signed net coefficient for every item:

```
k(item)  = products(item) - ingredients(item)           items per machine-second
k(craft) = S/T                                          crafts per machine-second

products(item)    = (S/T) * C(item) * (1 + P(item)) * p(item)
ingredients(item) = (S/T) * C(item)
```

where `S` is the machine speed including speed effects, `T` the recipe time, `C` the amount per craft, `P` the productivity bonus, and `p` the drop probability. Productivity applies only to the product side, and is zero for products flagged `ignored_by_productivity`.

An item that appears on both sides is netted (coal liquefaction nets `+65` heavy oil per craft). The sign of `k` says whether the recipe net-produces or net-consumes the item; an item netted to zero gives `inf`/`NaN`.

`EXPR in M` chooses the mode from the dimension of `EXPR`:

- `Q item/second in M` -> machines, `N = |Q| / |k(item)|`
- `Q item in M` -> machine-seconds, `tau = |Q| / |k(item)|`
- `Q crafts/second in M` -> machines, `N = |Q| / k(craft)`
- `Q crafts in M` -> machine-seconds, `tau = |Q| / k(craft)`

`in` requires an unscaled machine value on the right (exactly 1 machine, no accumulated time) and sets the count. Scale outside the `in`, not inside it.

The derived table has one row per item with a nonzero net coefficient, signed; rates in machines mode (`N * k`) and totals in machine-seconds mode (`tau * k`). The known row is what the user typed.

Arithmetic:

- multiplying or dividing by a dimensionless number scales the value
- division by zero yields `inf`/`NaN` in the output, multiplication by zero yields zero; neither is an error
- multiplying a machines value by a time gives machine-seconds; dividing a machine-seconds value by a time gives machines
- multiplying machine-seconds by a time, or dividing machines by a time, is an error
- addition requires the same mode and the same configuration and recipe; anything else is an error
- a machine value is a distinct type and does not mix with plain item values

### Configuration

The configuration resolves to slot usage, a speed multiplier, a per-product productivity bonus, and energy/pollution multipliers. Beacon effects are computed from the *total* number of beacons affecting the machine (the transmission factor depends on that count); per-beacon grouping only describes module composition and must not be applied independently. Efficiency modules do not change item rates (they only affect energy/pollution). Module count must fit the machine's slots, productivity must be allowed by the recipe, and the machine must be able to craft the recipe's category.

Machine power is well-defined per machine; beacon power and beacon item consumption are not determined by the value (they depend on how many machines share each beacon), so they are not part of it.

## Output

Each statement shows an output in the gutter.

- plain value and definitions: the value, formatted with the tab's time unit, the prefix toggle, and the global decimal limit
- machine value, machines mode: the machine count (fractional), every nonzero net item rate, crafts/s, and machine power
- machine value, machine-seconds mode: the craft count, every nonzero net item total, and machine time
- rows are labelled `produces` / `consumes` rather than shown as signed numbers
- errors show a message in the output cell and an inline marker; a line that references a failed value propagates the error

A machine value also gets a side panel for the focused line with the full breakdown. Exact layout is still open.

## Settings

All settings are global:

- max decimal places to display (`1/3` -> `0.333`)
- "use metric prefixes for items" toggle uses k/M/G in outputs where relevant (note that electricity always uses metric prefixes)
- time unit: second vs. minute vs. hour
- item rates display: `item/s`, or one of `yb`/`rb`/`bb`/`gb`/`syb`/`srb`/`sbb`/`sgb`; in a belt mode, item rates are shown as belt counts and the time unit does not apply to them
- belt stacking level, default 4

Settings may affect expression results (belt stacking does), not just display.

## Saving

All data is autosaved every ~5 seconds if any modifications were made, and on app shutdown. Losing a few seconds of work if the exit hook fails is acceptable.

The whole state is saved as a JSON blob: in order the tab texts, the settings, and a schema version. Tab titles are inferred from the first comment rather than stored. Tokens/icons are stored as plaintext prototype IDs inside the tab text, so the document content stays readable.

## Architecture

Crates:

- `hactorio` -- the egui/eframe app
- `hactorio-core` -- units, parser, evaluator; no egui dependency, testable headlessly
- `hactorio-data` -- game prototypes

Full document re-evaluation is acceptable, provided it runs on a non-UI thread and is cancelable.
