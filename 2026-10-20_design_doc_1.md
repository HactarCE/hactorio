# hactorio implementation notes

Syntax and semantics are defined in `2026-10-22_design_doc_2.md`. This document
keeps implementation details: tokens/icons, autocomplete, game data, saving,
architecture, and UI plumbing.

## 1. Document model

- The document is an ordered list of tabs; each tab is a sequence of lines.
- The active tab and per-tab cursor/scroll state are stored in the app.
- Tab titles are inferred from the first comment line: the text after the first
  `#`, trimmed. With no comment line or an empty title, the title is `Untitled`.
- Full re-evaluation is acceptable. The UI accepts results only for the current
  generation and discards older passes.

## 2. Tokens, icons, and saving text

### 2.1 One PUA codepoint per entry

- Namespace entries are sorted by prototype id; each gets a deterministic
  private-use codepoint in the BMP PUA.
- Signal aliases (`:stack-size:`, `:clock:`, `:lightning:`, ...) also participate
  in the PUA table. `:stack-size:` is not an ordinary namespace item.
- If an item and a recipe share a name, there is one entry and the item icon is
  used.
- Entries with no icon are still valid tokens.

### 2.2 Signals

Signals are a separate table from namespace entries.

- Fixed signal ids: `stack-size`, `clock`, `speed`, `lightning`.
- Fixed PUA glyphs: stack-size `F8FF`, clock `F8FD`, speed `F8FC`, lightning
  `F8FB`; the variable icon uses `F8FE`. `F8F0..F8FA` are reserved. Namespace
  entries use `E000..F8EF`; entry allocation stops below the reserved tail.
- Plaintext forms are `:stack-size:`, `:clock:`, `:speed:`, `:lightning:`.
  Save/load maps them to their fixed glyphs; lookup checks signals before
  entries.
- The lexer emits a signal token for these ids. `:stack-size:` is also a prefix;
  other signals are valid only after `.`.
- Signals are excluded from item autocomplete and offered only in property
  contexts.

### 2.3 Plaintext and PUA

A prototype token has two interchangeable forms: `:prototype-id:` and one PUA
codepoint. The lexer accepts both. In-memory text uses PUA; saved text uses
plaintext.

- Saving replaces every PUA codepoint with its `:id:` form.
- Loading replaces complete `:id:` tokens that name a current entry with PUA
  and leaves unknown text alone.
- Typing a complete `:id:` token that names a current entry converts it to PUA
  immediately.
- Parsing never depends on the conversion having run.

### 2.4 Glyph rasterization

- Proto/signal icons are rendered with a highest-priority `GlyphRasterizer`
  returning color glyph bitmaps; no font file is needed.
- The rasterizer is asked about every grapheme cluster, so it rejects
  non-PUA clusters with a fast check before lookup.
- Bitmaps are resized to the requested font size; `advance_px`/`offset_px` are
  set accordingly.
- Results are cached per cluster, family, and size. Replacing the PUA table
  means replacing the rasterizer so cached glyphs are dropped.
- Subscript digits in rate/capacity output are ordinary text, not PUA. On this
  machine every achievable monospace chain resolves U+2080–U+2089 (possibly via
  the bundled Ubuntu-Light fallback), so no tofu fallback is required. Some
  primary faces lack them natively and borrow a narrower fallback glyph, which
  can disturb grid alignment; if that matters, detect coverage from the primary
  face's cmap, not from `has_glyph` (which resolves the whole chain).

## 3. Autocomplete

One autocomplete system over the namespace, signals, properties, and variables.

### 3.1 Matching and ranking

- Case-insensitive `sublime_fuzzy` scoring against prototype id, localized name,
  and aliases. Matching rewards word starts and punishes long jumps.
- Ranking is score plus a small logarithmic popularity bonus. Popularity counts
  recipe ingredient/product references, built with the registry or loaded from
  cache.
- Variables add a fixed bonus, so a comparable match ranks above prototype ids
  while a clearly better id still wins.
- Aliases cover community names: `green-chip`/`green-circuit`, red/blue circuit
  variants, belt colors, `em-plant`, `<color>-science-pack`, planet names, etc.
- Signals are curated; do not offer every virtual signal as a normal value.
- Property names are matched as words. `electric` aliases the lightning signal;
  `prod` aliases `productivity`; `power` and `energy` remain strict word
  properties and do not insert the signal.

### 3.2 Popup behavior

- Accepting a prototype suggestion inserts the PUA codepoint. The popup replaces
  the current word, including a leading `:`.
- The popup is anchored at the caret and shows the glyph, the best matching
  name/alias, and the localized prototype name in a space-padded column.
- The selected row uses the normal text color for unhighlighted characters;
  matches are underlined.
- The popup is as wide as its widest visible row, capped at the window width.
- Up/Down move the selection, Enter/Tab accept, Escape dismisses until the word
  changes.
- The selected row scrolls into view on content/selection changes.
- Clicking a row accepts it.
- Tab accepts only while the popup is open; otherwise Tab moves focus.
- The popup opens only when text changes by typing, not by caret movement or
  clicking.
- Digit-leading words do not open the popup.

### 3.3 Contexts

- **Expression start:** items, fluids, machines, modules, beacons, the
  `:stack-size:` prefix, and variables.
- **After `.`:** properties, unit icons (`.:iron-plate:`), and signal aliases
  (`.:stack-size:`, `.:clock:`, `.:speed:`, `.:lightning:`). Do not offer
  arbitrary signal values.
- **After `with`:** modules, beacons, config values, and config variables.
- **After `making`:** recipes and recipe-bearing values.
- **After `in`:** machines, machine values, and unsolved process values.
- **After `:` inside plaintext:** prototype ids, as before.

Word boundaries are whitespace, operators (`+ - * / ^`), `.`, `=`, `(`, `)`,
`#`, and `,` if commas are added. `:` is not a word boundary; it belongs to a
plaintext token. A leading `:` is stripped from the query, but the replacement
range includes it, so accepting `:ipl` yields a PUA token.

When a word starts with a letter, adjacent `-`-separated segments are rejoined
for matching and replacement, so dashed aliases work. `.` starts a property
context and is not part of the word.

## 4. Game data

### 4.1 Import

- Locate the Factorio binary via Steam paths, then a file picker, and verify it
  with `--version`.
- Run `--dump-data` and `--dump-prototype-locale`.
- `--dump-data` writes `data-raw-dump.json`; the locale dump writes one
  `*-locale.json` per prototype type.
- Output lands in the Factorio user-data directory's `script-output`.
- Post-process into a compact cache in app data. Icons are not dumped; icon
  paths are recorded and read from game data/mods at runtime.
- `--dump-icon-sprites` is not used; it writes nothing on at least 2.1.23 on
  macOS.
- The enabled mod set is used automatically.
- No quality variants are modelled.

Post-processing responsibilities relevant to the language:

- Every prototype with a `stack_size` is a namespace item; modules keep their
  effects.
- Blueprint parameters (`parameter-N`) are excluded.
- Minable resources get synthetic recipes.
- Recipes with no products are dropped; product probabilities are folded into
  expected amounts.
- Machines are joined from items to entities with crafting/resource categories.
- Beacons are collected with slots, allowed effects, distribution effectivity,
  profile, and energy usage.
- Container `inventory_size` and fluid capacities are joined to items.
- Belt items record their entity speed for the base slot rate
  (`speed × 60 × 8`).
- Inserter capacity modifiers and research effects are collected, including the
  effects for `inserter-stack-size-bonus` and
  `bulk-inserter-capacity-bonus`.
- Equipment prototype power and stored-energy fields are joined to their item
  entries.
- Generic item entity `energy_usage` is recorded for `.power` (radar, beacons,
  etc.).
- Virtual signals used by the language are collected/aliased.

### 4.2 Loading

- The app loads an existing post-processed cache at startup if present.
- A "Load game data" button runs the dump and post-processing pipeline.
- There is no automatic change detection. A reload happens only on request.
- If locating/dumping/post-processing fails, the existing data and codepoint
  table remain in use.

On a successful load:

1. Canonicalize every open tab to `:id:` plaintext using the old table.
2. Install the new prototype/signal data and codepoint table.
3. Replace the glyph rasterizer.
4. Re-lex every tab from plaintext with the new table.
5. Re-evaluate.
6. Clear the expression cache.

Until the first successful load, the editor/results are hidden; only
"Game data is not loaded yet" and a load button are shown. The action reads
"Load game data" before the first load and "Reload game data" afterwards.

Autosave is paused during the swap. A crash during the swap leaves the saved
document as plaintext, still loadable.

### 4.3 Cache versioning

The registry schema changes with facets (signals, beacons, containers, inserter
data, entity power). Bump or invalidate the cache when those fields change, and
require a game-data reload.

## 5. Saving

- Autosave every ~5 seconds if modified, and on shutdown.
- Each save writes a temporary file in the same directory and renames it over the
  real file.
- The write runs on a background thread; the UI hands over an immutable
  snapshot.
- The state is a version-first JSON object:

```json
{
  "version": 1,
  "tabs": ["# Main\nrate = 3 :iron-plate: / second"],
  "active_tab": 0,
  "cursors": [{"line": 0, "column": 0, "scroll": 0.0}],
  "window": {"width": 1280.0, "height": 800.0, "maximized": false},
  "results_width": 380.0,
  "zoom": 1.0,
  "font_size": 13.0,
  "settings": {
    "max_decimals": 3,
    "metric_prefixes": true,
    "time_unit": "second",
    "item_rate_belt": null,
    "stacked_belts": false,
    "belt_stacking": 4,
    "inserter_capacity": 0,
    "research_levels": {}
  }
}
```

- Tab text is stored as plaintext `:prototype-id:`.
- Missing settings fields use defaults; `inserter_capacity` defaults to 0, so no
  save migration is required.
- Settings may affect evaluation (belt stacking level, inserter capacity
  research, productivity research levels) or display only; see the semantics
  document.
- Autosave is paused during the game-data swap.

## 6. Architecture

Crates:

- `hactorio` — egui/eframe app.
- `hactorio-core` — values, parser, evaluator, settings; no egui dependency.
- `hactorio-data` — game prototypes, dumps, cache, icons.

Core entry point:

```rs
fn evaluate(
    doc: &str,
    settings: &Settings,
    registry: &Registry,
    cache: &mut LineCache,
) -> Vec<StatementOutput>;
```

- `doc` is one tab.
- `LineCache` maps a line key to a parsed AST, never an evaluated result.
- The key is the line text (hash acceptable).
- Parsed expressions store resolved prototype ids, property/signal selectors,
  a `:stack-size:` prefix flag, and machine/process/rate/capacity structure. The
  belt stacking level is read from settings at evaluation time and is never
  embedded in the AST.
- Settings do not affect parsing; changing settings must not invalidate the
  parse cache.
- Game-data reload clears the cache.
- A pass parses cache misses, evaluates every line, then drops cache entries not
  seen.
- Duplicate line texts share one cache entry.

Threading:

- One evaluator thread owns the cache.
- The app sends a document snapshot, settings snapshot, `Arc<Registry>`
  snapshot, and generation number.
- Latest-pass-wins: results for older generations are discarded.
- While a pass runs, previous outputs are painted only for lines whose current
  text matches the text they were computed from.

## 7. UI Notes

- The results column is a resizable side panel inside the editor's scroll area;
  width is saved with the document.
- Gutter results truncate with `…`; the focused line replaces its gutter result
  with a floating details panel.
- Hovering an icon or a variable opens a details popup.
- The details popup groups prototype properties by kind; a prototype that is
  both an item and a machine shows both groups.
- Variable details show the name and formatted value; machine and process
  values include derived details from the same evaluation.
- The floating details panel shows all facets of a value; the single-line
  gutter shows the first present of item, machine, process, config, then falls
  back to rate, capacity, then recipe.
- The Display and Research bars reserve a shared label column, then pack
  settings into as many rows as fit. Each row scrolls horizontally when a
  single setting is wider than the column.
