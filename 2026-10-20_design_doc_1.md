# hactorio design

The app is a text document with tabs.
Each statement line has an output off to the side, which updates automatically.

## 1. Overview

- The document is an ordered list of tabs; each tab is a sequence of lines.
- A line is one statement, a comment, or blank.
- Variables are tab-scoped and visible only to later lines in the same tab.
- Fuzzy autocomplete covers every item, fluid, and recipe (machine and module prototypes are items, so they are included automatically).
- Game data and icons live in app data, never in the repo.

Tab UI behavior (creating, closing, reordering, presenting tabs) is out of scope for this document.
The data model is an ordered list of tab texts plus the active tab index.

## 2. Tokens, icons, and autocomplete

### 2.1 One namespace

Prototype tokens resolve against a single namespace of items, fluids, and recipes.
Modules are their own prototype type but are namespace entries, and a machine is an item whose corresponding entity declares crafting or resource categories, so both are in that namespace.

- If an item and a recipe share a name, there is **one** autocomplete entry, using the item's icon.
- Outside `making`, such a token resolves as the item; `@` converts a machine item to a `MachineValue` (2.5).
- After `making`, the same token resolves as the recipe.
- A recipe-only name is an entry with the recipe icon; it is only legal after `making`.
- A token whose name has no item, fluid, module, or recipe is an unknown prototype and is an error.

### 2.2 Token syntax

A prototype token has two interchangeable forms:

- **Plaintext:** `:prototype-id:`, e.g. `:iron-plate:` or `:assembling-machine-3:`.
- **PUA:** one private-use codepoint assigned to the namespace entry.

The lexer accepts both forms and maps them to the same namespace entry.
Colons are reserved for prototype tokens; a `:` outside a `:id:` token is a parse error outside comments.
`@` is punctuation that prefixes a machine-item token; it is not part of the ID.

In-memory text uses PUA characters.
Saved text uses the `:prototype-id:` form.

- Saving replaces every PUA codepoint with its `:id:` form (a plain find-and-replace).
- Loading scans the plaintext, replaces every complete `:id:` token that names a current entry with its PUA codepoint, and leaves unknown `:id:` text alone.
- Typing a complete `:id:` token that names a current entry converts it to PUA immediately.
- Because the lexer accepts plaintext directly, parsing never depends on the conversion having run.

### 2.3 Icons

- One PUA codepoint per namespace entry, assigned deterministically (sorted by prototype ID) and stored in the app-data cache.
- If an item and recipe share a name, the item icon is used for that entry.
- A recipe-only entry uses the recipe icon.
- Rendered via `Context::add_glyph_rasterizer` as a highest-priority `GlyphRasterizer` returning color glyph bitmaps; no font file is needed.
- A highest-priority rasterizer is asked about *every* grapheme cluster, so it MUST reject non-PUA clusters with a single fast check before doing any lookup.
- The bitmap is resized to the requested font size, and `advance_px`/`offset_px` are set accordingly.
- Results are cached per cluster, family, and size. When the codepoint table changes, replace the rasterizer (`set_glyph_rasterizers`) so the old glyph cache is dropped.
- Unknown `:id:` tokens stay plaintext and are a parse error.

### 2.4 Autocomplete

One autocomplete system over the whole namespace.

- Matching uses case-insensitive `sublime_fuzzy` scoring against the prototype ID, the localized name, and aliases; matched characters are highlighted in the popup.
- Aliases cover common community names: `green-chip`/`green-circuit` for `electronic-circuit`, red and blue variants for `advanced-circuit` and `processing-unit`, belt colors (`yellow-belt`, `red-belt`, `blue-belt`, `green-belt`), `em-plant` for `electromagnetic-plant`, `<color>-science-pack` for the science packs, and planet names such as `vulcanus-science-pack`.
- Accepting a suggestion inserts the entry's PUA codepoint. The popup replaces the current word itself, including a leading `:`.
- The popup is anchored at the caret. It shows the entry's glyph (so the icon comes from the same rasterizer as the text) followed by the single best-matching name or alias, then the localized prototype name in a space-padded column. The display-only content is never parsed back.
- When the query matches the prototype name itself, the canonical ID is shown in the first column and the matched prototype name in the second.
- The selected row uses the standard text color for unhighlighted characters; only the matched characters are underlined.
- The popup is as wide as its widest visible row, capped at the window width, so entries do not wrap.
- Up and Down move the selection, Enter and Tab accept, and Escape dismisses until the word changes.
- The selected row is scrolled into view whenever the contents or selection change and whenever the popup opens.
- Clicking anywhere on a row accepts it.
- Tab accepts only while the popup is open. Otherwise Tab moves keyboard focus as usual, as does Shift+Tab in every state.
- The popup opens only when the text changes by typing; moving the caret or clicking into the editor does not open it.
- Words that start with a digit do not open the popup.
- Word boundaries for `CompletionPopup` are whitespace, operators (`+ - * / ^`), `@`, `=`, `(`, `)`, and `#`.
- When the word under the caret starts with a letter, adjacent `-`-separated segments are rejoined for matching and replacement, so dashed aliases and IDs such as `green-chip` work as one word.
- `:` is **not** a word boundary: it is part of a plaintext prototype token. A leading `:` is stripped from the query for matching, but the replacement range includes it, so accepting `:ipl` yields a PUA token rather than a stray colon.
- In `@` context only machine-capable entries are offered; accepting `@ipl` replaces `ipl` and leaves the `@` in place.
- In `making` context the same entries are offered; selecting a name that has no recipe is an error.
- Every namespace entry is offered, including hidden recipes such as recycling. There is no filtering by prototype kind or visibility.

### 2.5 Prototype token resolution

Resolution is contextual:

- **Expression operand:** an item/fluid token is a `Scalar`, including a machine item. A recipe-only token is an error.
- **Machine head:** `@` followed by an item token whose ID names a machine prototype forms a `MachineValue`. A machine prototype is an item whose corresponding entity declares a non-empty `crafting_categories` (crafting machines) or `resource_categories` (mining drills).
- **Module position:** the token must name a module item.
- **After `making`:** the token must name a recipe.

`@` is the only way to form a machine value: `:foundry:` is the foundry item, and `@:foundry:` is one foundry.
`@` applies to the following item token only. `@(:foundry:)`, `@x`, `@2`, `@:iron-plate:`, and `@` on a recipe-only name are errors.
This is final: `@` never applies to variables or expressions, so there is no `@m` form.

## 3. Syntax

### 3.1 Numbers

- Decimal only: `3`, `3.`, `.5`, `1.25`.
- Metric prefixes are suffixes on the number: `3k`, `1.5M`, `250G`.
- `3 k` is not valid; `k` alone is not a token.
- There is no exponent notation (`1e3`) and no digit separators (`1_000`).
- A number followed directly by a unit word or a prototype token is a quantity literal: `3 minute` is three minutes and `3 :iron-plate:` is three iron plates. Juxtaposition is not an operator, so `3 4`, `3 (x)`, and `3 x` are errors.

### 3.2 Operators and precedence

Operators: `+ - * / ^`, parentheses, `in`, and the machine-conversion prefix `@`.

- `@` is a prefix that converts the following machine-item token to a `MachineValue`: `@:foundry:`. It is not a general expression operator and does not apply to variables or parenthesized expressions.
- Unary minus only; there is no unary plus.
- `^` is right-associative.
- Unary minus binds looser than `^`, so `-2^2` is `-4`, and `2^-2` is `0.25`.
- `^` on a dimensionless value is real-valued: `4^0.5` is `2`.
- On a unit-bearing value the exponent must be an integer. A fractional exponent is an error even if it would divide the unit exponents evenly.
- A negative exponent is valid, including on a unit-bearing value: `:iron-plate:^-1` is a legal monomial.
- `in` has the lowest precedence. Its right operand is any expression that evaluates to a machine value; it is parsed at unary precedence, so it ends at the next operator, `)`, `#`, or newline. A machine spec is the usual form, but variables holding a machine value and parenthesized machine values are allowed.
- `in` is non-associative; `a in b in c` is a parse error.

Precedence, tightest first:

1. `^` (right-associative)
2. unary `-`
3. `*` `/`
4. `+` `-`
5. `in`

Consequences:

- `Q * 2 in M` is `(Q * 2) in M`.
- `Q in M * 2` is `(Q in M) * 2`, because the machine spec on the right ends at `*`.
- `a + b in M` is `(a + b) in M`.
- To scale the result of `in`, write `3 * (Q in M)`.

### 3.3 Statements and variables

Statements are explicit:

```
name = EXPR     # definition; binds EXPR and shows its value
EXPR            # anonymous expression; shows its value
# comment
```

- One statement per line; a newline terminates the statement.
- Variables are ad-hoc and may hold units: `rate1 = 3 :iron-plate: / second`.
- Variables may hold any evaluated type: `Scalar`, `MachineValue`, or `RecipeValue`.
- Variables are visible only to later lines in the same tab; there is no visibility across tabs.
- A variable name is a bare identifier `[A-Za-z_][A-Za-z0-9_]*`. Bare identifiers contain no hyphens, so `-` outside a `:id:` token is always subtraction.
- Defining a name that collides with a reserved bare word or with any prototype ID is an error.
- Variables cannot be redefined or shadowed within a tab; a second definition of an already-bound name is an error, not a rebind.
- A definition that fails still binds its name, as a poisoned value; references to it propagate the original error.
- `EXPR in MACHINE` is an expression, not a statement-level clause.

Reserved bare words: `in`, `making`, `second`, `s`, `minute`, `m`, `hour`, `h`, `joule`, `watt`, `craft`, and the belt tokens `yb`, `rb`, `bb`, `gb`, `syb`, `srb`, `sbb`, `sgb`.
`k`, `M`, and `G` are numeric suffixes, not identifiers.
`machine` is not a token.

### 3.4 Comments

Comments start with `#` and run to the end of the line.
A `#` also terminates a machine spec.
Blank and comment lines have no output.

## 4. Values

A value is a single monomial: a coefficient plus an integer exponent for each base unit.

```rs
struct Value {
    coef: f64,
    /// Exponent per base unit. Zero exponents are removed; iteration is sorted.
    units: BTreeMap<BaseUnit, i64>,
}
```

Base units are:

- every item and fluid prototype (opaque IDs);
- `second`;
- `joule`;
- `craft`.

Recipes do not get base units.
`machine` is not a base unit and never appears in a `Value`'s unit map; it lives in `MachineValue`/`RecipeValue`.
`craft` **is** a real base unit: `3 craft` and `3 craft / second` are ordinary values.

A `Value` is always canonical: it holds base units only, with every alias already folded into `coef`.
It carries no record of how the user spelled the unit, so two values with the same coefficient and units are equal regardless of syntax.

What an expression evaluates to is an enum, because a machine value and a recipe value are distinct types:

```rs
enum Eval {
    Scalar(Value),
    Machine(MachineValue), // machines + modules, no recipe
    Recipe(RecipeValue),   // machines + modules + recipe + quantity
}
```

Rules:

- `100 :iron-plate: / second` is one value; `3 :gear: / minute` is another.
- Addition and subtraction require identical units (same map); coefficients are combined.
- Multiplication adds exponents, division subtracts them, `^` multiplies them.
- The exponent must be an integer when the value has units.
- Adding different items is an error; there is no sum-of-different-items value.
- `craft` does not convert to items. It is a normal scalar unit; its only special use is selecting the craft column when used as the left operand of `in`.

## 5. Units

### 5.1 Metric prefixes

- Suffixes on numeric literals: `k`, `M`, `G` (`3k` = 3000, `1.5M` = 1,500,000).
- They are parse-time and display-time only; they are not part of the value.
- `3k :iron-plate:` produces `3000 :iron-plate:`.
- That displays as `3k :iron-plate:` only if the item-prefix toggle is on.
- Electricity always uses metric prefixes, regardless of the item toggle.

### 5.2 Time

- `second` is the only time base unit.
- `minute` (60 s) and `hour` (3600 s) are parse-time aliases folded into `coef`.
- `s`, `m`, and `h` are aliases for `second`, `minute`, and `hour`, so `3 m` is the same value as `3 minute`. Aliases never reach the value or the output; only the global time unit decides how time is displayed.
- `3 minute` is `Value { coef: 180.0, units: { second: 1 } }`.
- Nothing downstream ever sees `minute` or `hour`.

### 5.3 Electricity

- `joule` is a base unit.
- `watt` is a parse-time alias for `joule / second`, i.e. `joule * second^-1`.

### 5.4 Belt rates

Belt throughput is a literal form, not a unit:

```
2 yb :iron-plate:   == 30 :iron-plate: / second
1 gb :gear:         == 60 :gear: / second
yb :iron-plate:     == 15 :iron-plate: / second
```

- The count precedes the belt token, is a positive number, and defaults to 1.
- `yb` / `rb` / `bb` / `gb` are 15 / 30 / 45 / 60 items per second.
- `syb` / `srb` / `sbb` / `sgb` are the same multiplied by the effective stack size, `min(global stacking level, item stack size)`.
- The token after the belt token must be a single item prototype token, not a fluid, variable, or expression.
- The result is sugar for a `second^-1` rate: `N BELT ITEM` is `N * RATE * ITEM / second`. Once formed it is an ordinary value, so further arithmetic such as `/ second` is allowed.
- The global time-unit setting never changes the value, only how it is displayed.
- Belt stacking is applied during evaluation, not parsing; the parsed form stores the belt tier and whether it was a stacked token.

### 5.5 No other conversions

There are no ad-hoc unit relations and no cross-item conversion: `:iron-plate:` and `:gear:` are distinct dimensions that never convert into each other.

There is no `EXPR to UNIT` syntax.

## 6. Game data

Imported from the installed game; nothing is bundled or redistributed.

- Locate the Factorio binary via Steam library paths, then a file picker, and verify it with `--version`.
- Run `--dump-data` and `--dump-prototype-locale`.
- Each dump flag loads the data stage with the configured mod set, writes its output, and exits.
- `--dump-data` writes `data-raw-dump.json`; `--dump-prototype-locale` writes one `*-locale.json` per prototype type.
- Output lands in `script-output` inside the Factorio *user data directory* (e.g. `~/Library/Application Support/factorio/script-output` on macOS), not next to the binary.
- Post-process into a compact cache in app data; the cache and icons are owned by the app, never by the repo.
- Icons are not dumped. Every prototype's `icon` is a path into game data or a mod, which the cache records and the app reads directly. `--dump-icon-sprites` is not used: it writes nothing on at least 2.1.23 on macOS.
- The enabled mod set is what the dump uses and is included automatically.
- The dump has no quality variants; quality is a runtime modifier. Only normal quality is modelled.

Post-processing:

- Items are spread across prototype types (`item`, `ammo`, `gun`, `armor`, `capsule`, `module`, ...): every prototype with a `stack_size` is a namespace item. Modules also keep their effects.
- Blueprint parameters (`parameter-N`) are excluded.
- A minable resource has no recipe in the dump, so one is synthesized: its category is the resource's (`basic-solid` when absent), its craft time is `minable.mining_time`, and its product is the resource's result. This is what makes mining drills usable as machines.
- Recipes with no products are dropped.
- Product probabilities are folded into an expected amount (7.3).

Loading is explicit:

- The app loads an existing post-processed cache at startup if one is present.
- A "Load game data" button runs the dump and post-processing pipeline again.
- There is no game-data cache key and no automatic change detection; a reload happens only when the user asks for one.
- If locating the binary, dumping, or post-processing fails, the existing data and codepoint table remain in use.

On a successful load:

1. Canonicalize every open tab to `:id:` plaintext using the old codepoint table.
2. Install the new prototype data and codepoint table.
3. Replace the glyph rasterizer (so cached glyphs are dropped).
4. Re-lex every tab from plaintext with the new table, back to PUA.
5. Re-evaluate.
6. Clear the expression cache.

Autosave is paused for the swap. If the process dies during the swap, the saved document is still plaintext and remains loadable.

## 7. Machine and recipe values

A machine spec denotes one or more machines with a fixed configuration, optionally running one recipe.

```rs
struct MachineValue {
    machine: MachineId,
    modules: Vec<(ModuleId, u32)>,
    count: f64, // machines
}

struct RecipeValue {
    machine: MachineId,
    modules: Vec<(ModuleId, u32)>,
    recipe: RecipeId,
    quantity: RecipeQuantity,
}

enum RecipeQuantity {
    Machines(f64),        // machine
    MachineSeconds(f64),  // machine * second
}
```

`RecipeQuantity::MachineSeconds` holds an amount of machine time, `tau`.
A bare machine spec without `making` evaluates to `MachineValue`.
A spec with `making` evaluates to `RecipeValue` with `RecipeQuantity::Machines(count)`.

### 7.1 Grammar

```
machine-spec := count? '@' MACHINE module* (making RECIPE)?
module       := count? MODULE
count        := NUMBER   // positive integer
```

- Counts come **before** the token they describe.
- A machine count is optional and defaults to 1: `3 @:assembling-machine-3:` is three machines.
- Module counts are optional and default to 1: `@:assembling-machine-3: 3 :productivity-module-2:`.
- `@` is required to form a machine spec; `:assembling-machine-3:` without `@` is the machine item as a scalar.
- Counts in a machine spec are positive integers. Scaling by a dimensionless value can produce a fractional machine count.
- Duplicate modules merge (their counts add) before validation.
- The machine token after `@` must name a machine prototype: an item whose corresponding entity declares a non-empty `crafting_categories` or `resource_categories` (mining drills). Whether the machine is a crafting machine or a drill decides which of the two lists capability is checked against.
- Module tokens must name module items.
- `making` is optional; the token after it must be a recipe.
- The spec extends to the next newline, operator, `)`, or `#`.
- A machine spec inside a larger expression needs parentheses to end it: `3 * (100 :electronic-circuit: / second in @:assembling-machine-3: making :electronic-circuit:)`.

Example, mechanically valid:

```
@:foundry: 3 :productivity-module-2: 1 :speed-module-3: making :iron-plate:
```

- The machine is a foundry, with 4 module slots (3 + 1).
- Iron plate accepts productivity modules.
- The foundry can craft iron plate.
- The machine count is 1 (the default); the `3` is the productivity-module count, because counts precede the token they describe.

### 7.2 Recipe resolution

- If `making` is present, that recipe is used.
- If `making` is omitted, the spec is a bare `MachineValue` (`@` + machine token). When it is used as the right operand of `in`, the recipe is resolved from the left operand's item/fluid: it must have exactly one producing recipe that the machine can craft. Zero or multiple candidates is an error.
- A craft quantity has no item to resolve a recipe, so `Q craft` and `Q craft/second` require an explicit `making RECIPE`.
- With `making`, a `RecipeValue` can stand alone without an `in`.
- The machine must be able to craft the recipe's category: any of the recipe's categories must be in the machine's `crafting_categories` for a crafting machine, or in its `resource_categories` for a mining drill. A drill's recipe for an ore is the synthesized one from 6.

### 7.3 Net coefficients

For a fixed configuration and recipe:

```
k(item)  = products(item) - ingredients(item)           items per machine-second
k(craft) = S/T                                          craft per machine-second

products(item)    = (S/T) * (C(item) + P(item) * (C(item) - I(item)))
ingredients(item) = (S/T) * C(item)
```

where:

- `S` is the machine speed including speed effects.
- `T` is the recipe time.
- `C(item)` is the **expected** amount per craft, computed when the cache is built: the prototype's `amount` scaled by its probability (its `independent_probability`, or the width of its `shared_probability` range, default 1) plus `extra_count_fraction`.
- `P(item)` is the productivity bonus.
- `I(item)` is the part of a product that productivity ignores (`ignored_by_productivity`, an amount in 2.x data, not a flag).

Productivity applies only to the product side, and only to `C(item) - I(item)`.
Productivity modules are legal only if the recipe allows productivity.

An item that appears on both sides is netted (coal liquefaction nets `+65` heavy oil per craft).

The sign of `k` says whether the recipe net-produces or net-consumes the item; `k = 0` gives `inf`/`NaN` when used as a divisor.
`k(craft)` is derived; the `craft` unit itself is a real base unit.

### 7.4 `in`

`EXPR in M` chooses the quantity from the dimension of `EXPR`:

- `Q :item:/second in M` -> machines, `N = Q / |k(item)|`
- `Q :item: in M` -> machine-seconds, `tau = Q / |k(item)|`
- `Q craft/second in M` -> machines, `N = Q / k(craft)`
- `Q craft in M` -> machine-seconds, `tau = Q / k(craft)`

The sign of `Q` is kept, so a negative rate yields a negative machine count (or negative machine time) rather than silently meaning the same as the positive one.

Any other dimension is an error: `100 joule/second in M`, `100 :iron-plate: * second in M`, `:iron-plate:^2 / second in M`, `3 craft^2 in M`, and a plain number all fail to select a quantity.

`in` requires the right operand to evaluate to exactly one machine with no accumulated machine time:

- a bare `MachineValue` with count 1 (recipe resolved from `EXPR`), or
- a `RecipeValue` with `RecipeQuantity::Machines(1.0)`.

The right operand may be a machine spec, a variable holding a machine value, or a parenthesized machine value.

`3 @:assembling-machine-3:` is not a valid right operand; scale outside instead:

```
3 * (100 :electronic-circuit: / second in @:assembling-machine-3: making :electronic-circuit:)
```

### 7.5 Derived table

The derived table has one row per item/fluid with a nonzero net coefficient, signed.

Rows hold rates when the quantity is `Machines` (`N * k`) and totals when it is `MachineSeconds` (`tau * k`).

The known row is the dimension the user typed on the left of `in`: the item/fluid row for item operands, or the `craft` row for craft operands.
If that coefficient is zero, there is no row and the resulting machine count/time is `inf`/`NaN`.

### 7.6 Machine arithmetic

- Multiplying or dividing by a dimensionless number scales the value.
- Division by zero yields `inf`/`NaN` in the output, multiplication by zero yields zero; neither is an error.
- Multiplying a `RecipeValue` with `Machines` by a time gives `MachineSeconds`; dividing a `MachineSeconds` value by a time gives `Machines`.
- Multiplying `MachineSeconds` by a time, or dividing `Machines` by a time, is an error.
- Addition requires the same `RecipeQuantity` variant, the same configuration and the same recipe for `RecipeValue`; for `MachineValue`, the same machine and modules. Adding `Machines` to `MachineSeconds` is a type error: there is no coercion between the two.
- A `MachineValue` does not support time arithmetic; `in` is the only bridge from a bare machine value to a `RecipeValue`.
- Multiplying or dividing two machine values is an error.
- Unary minus and `^` apply to scalars only.
- `Scalar`, `MachineValue`, and `RecipeValue` do not mix. A `MachineValue` and a `RecipeValue` are distinct types.

### 7.7 Configuration and validation

The configuration is the machine prototype and its modules; it resolves to slot usage, a speed multiplier, a per-product productivity bonus, and energy/pollution multipliers.

Quality:

- The machine and its modules are assumed to be normal quality.
- Quality variants in the dump are ignored, and no quality token appears in a machine spec.

Modules:

- Efficiency modules do not change item rates; they only affect energy/pollution.
- Total module count must fit the machine's slots.
- A module's category effect must be allowed by the machine: speed modules need `speed`, productivity modules need `productivity`, efficiency modules need `consumption`, quality modules need `quality`. Effects the machine does not allow are ignored when the module's bonuses are applied.
- Productivity modules require a recipe that allows productivity once a recipe is known. A bare `MachineValue` may carry them; the check happens when `making` or `in` attaches a recipe.
- The machine must be able to craft the recipe's category once a recipe is known.
- Counts in the spec must be positive integers.

Power:

- For a `RecipeValue`, per-machine active power is well-defined from the prototype's energy usage and the recipe's module effects.
- A bare `MachineValue` has no recipe, so no active power is reported.
- Pollution per minute is unitless and scales with both module effects: `emissions_per_minute * (1 + sum of consumption effects) * (1 + sum of pollution effects)`. This was confirmed in game on a tier-3 assembler: 2/min base, 3.96/min with one productivity-module-3, 6.24/min with two. Negative emissions, such as the biochamber's, reduce pollution and keep their sign.
- No layout or distance modelling is done; all listed modules act on the machine directly.

## 8. Output

Each statement shows an output in the gutter.

- `Scalar`: the value, formatted as below.
- `MachineValue`: the machine count. Bare machine values have no recipe-dependent output (no rates, craft counts, or power).
- `RecipeValue` with `RecipeQuantity::Machines`: the machine count (fractional), every nonzero net item/fluid rate, `craft/s`, per-machine active power, and total power `N * per-machine` when `N != 1`.
- `RecipeValue` with `RecipeQuantity::MachineSeconds`: the craft count, every nonzero net item/fluid total, machine time, and total energy `tau * per-machine power`.
- Rows are prefixed with `+` (produced) or `-` (consumed) rather than shown as signed numbers.
- The known row is the operand row (item/fluid or `craft`); if it is absent from the table, the machine count/time is shown as `inf`/`NaN`.
- Errors show a message in the output cell and an inline marker.
- A definition that fails binds a poisoned value; a line that references a poisoned value propagates the error.
- Units within a value are printed sorted by exponent (decreasing), then alphabetically by name.
- Positively-exponented units form the numerator and negative ones the denominator, so `{iron-plate: 1, second: -1}` prints as `:iron-plate:/s`, with no spaces around the `/`.
- Exponents above one print as `^n`, e.g. `second^2`. Multiple numerator units are joined with `*`; multiple denominator units are parenthesized and joined with `*`, e.g. `:iron-plate: / (joule * second)`. An empty numerator prints as `1`, so `second^-1` is `1 / second`.

Formatting:

- Scalars use the global time unit, the item-prefix toggle, and the global decimal limit.
- `craft` prints as `craft`; rates as `craft/s`.
- In belt display mode, item rates are shown as belt counts. Fluid rates ignore the belt mode.
- In belt mode the time unit does not apply to item rates; fractional belt counts are allowed.
- Machine time uses the global time unit.
- Machine time is written `<machine-glyph>·<time-unit>`, e.g. `0.4 <glyph>·s`, because it is machine-seconds.
- Machine power is written `<power> /<machine-glyph>`.
- Time units are displayed in their short forms: `s`, `m`, and `h`.

The results column is a resizable side panel inside the editor's scroll area, so both scroll together. Its width is saved with the document.

Gutter results are truncated with `…` when they do not fit. The focused line replaces its gutter result with a floating panel: headline, produced and consumed amounts in two columns, craft, and power, untruncated.

Hovering an icon in the editor, the gutter results, or the floating panel shows the line's detailed breakdown in a popup. The breakdown popup may appear on top of the floating panel.

The breakdown shows:

- the machine configuration: machine, count, modules with counts, slots used and capacity, speed, productivity, and consumption multipliers;
- the recipe: name, categories, craft time, and whether productivity is allowed;
- per item: produced, consumed, and net amounts, at the line's quantity;
- power: base energy usage, per-machine watts, total watts when `N != 1`, and energy per craft or total energy;
- pollution per minute per machine, and total pollution;
- notes for ignored-by-productivity amounts, disallowed module effects, and modules that do not change rates.

The breakdown is derived from the same evaluation and never changes the value.

## 9. Settings

All settings are global.

- Max decimal places to display (`1/3` -> `0.333`); default 3.
- "Use metric prefixes for items" toggle, which uses `k`/`M`/`G` in outputs where relevant; default on. Electricity always uses metric prefixes.
- Time unit: second vs. minute vs. hour; default second.
- Item rates display: `item/s`, or a belt tier (`yb`/`rb`/`bb`/`gb`); default `item/s`. In a belt mode, item rates are shown as belt counts and the time unit does not apply to them. Fluids ignore belt mode. Belt mode wins over the metric-prefix toggle for item rates.
- Stacked belts for item rates: whether belt-mode item rates use stacked belts (`syb`/`srb`/`sbb`/`sgb`); default off.
- Belt stacking level: 1, 2, 3, or 4 only; default 4.

Settings may affect expression results (belt stacking does), not just display.

`Settings` therefore lives in `hactorio-core` and is passed *into* evaluation.
The app holds one copy and hands out a snapshot, so the evaluator never reaches back into UI state.

Belt stacking is applied when a belt literal is evaluated, not when it is parsed.
The parsed form stores the belt tier and whether it was a stacked token, so the expression cache is independent of settings.

## 10. Saving

All data is autosaved every ~5 seconds if any modifications were made, and on app shutdown.
Losing a few seconds of work if the exit hook fails is acceptable.

Each save writes to a temporary file in the same directory and then renames it over the real one, so a crash or kill mid-write can never truncate the document.
The write itself runs on a background thread; the UI thread only hands over an immutable snapshot.

The whole state is saved as a version-first JSON object:

```json
{
  "version": 1,
  "tabs": [
    "# Main\nrate = 3 :iron-plate: / second",
    "# Second\n"
  ],
  "active_tab": 0,
  "cursors": [
    { "line": 3, "column": 7, "scroll": 0.0 },
    { "line": 0, "column": 0, "scroll": 0.0 }
  ],
  "window": {
    "x": 100.0,
    "y": 100.0,
    "width": 1280.0,
    "height": 800.0,
    "maximized": false
  },
  "results_width": 380.0,
  "zoom": 1.0,
  "font_size": 13.0,
  "settings": {
    "max_decimals": 3,
    "metric_prefixes": true,
    "time_unit": "second",
    "item_rate_belt": null,
    "stacked_belts": false,
    "belt_stacking": 4
  }
}
```

- `tabs` is in tab order; `cursors` has one entry per tab.
- The active tab, per-tab cursor/scroll state, window geometry, the width of the results column, the GUI zoom factor, and the editor font size are saved.
- Tab titles are inferred from the first comment line rather than stored: the first line beginning with `#` provides the title after the `#`, trimmed; if there is no comment line, or the trimmed title is empty, the title is `Untitled`.
- Tokens/icons are stored as `:prototype-id:` plaintext in the tab text, so the document content stays readable.
- Schema migration and multi-instance coordination are out of scope.
- Autosave is paused during the game-data swap.

## 11. Architecture

Crates:

- `hactorio` -- the egui/eframe app.
- `hactorio-core` -- units, parser, evaluator, settings; no egui dependency, testable headlessly.
- `hactorio-data` -- game prototypes, dumps, cache, icons.

Full document re-evaluation is acceptable.
The core has one entry point with no interior mutability; the expression cache is an explicit argument:

```rs
fn evaluate(
    doc: &str,
    settings: &Settings,
    reg: &Registry,
    cache: &mut LineCache,
) -> Vec<StatementOutput>;
```

- `doc` is one tab.
- `LineCache` maps a line key to its parsed expression (AST), never an evaluated result.
- The key is the line's text (a hash is acceptable, but the text is small and avoids collision concerns).
- Parsed expressions store resolved prototype IDs and belt tier/stacked flags; they do not store evaluated coefficients, per-line results, or settings snapshots.
- Settings do not affect parsing, so changing settings does not invalidate the cache.
- Game-data reload clears the cache.
- A pass parses only cache misses, evaluates every line, and then drops every cache entry not seen during the pass.
- Duplicate line texts share one cache entry.

Threading and cancellation:

- A single evaluator thread owns the cache.
- The app sends a document snapshot, settings snapshot, `Arc<Registry>` snapshot, and a generation number.
- Latest-pass-wins: the UI accepts results only for the current generation and discards older ones. In-flight passes are not cancelled; they finish and are discarded.
- While a pass runs, the previous outputs are painted only for lines whose current text matches the text they were computed from (store the source text or its hash with each output). Lines that changed show no stale output rather than an output shifted onto the wrong line.

`StatementOutput` carries at least:

- the line index and the source line hash,
- the span of the statement/error within the line,
- the result (scalar/machine/recipe output, or an error with a span).

No synchronization is needed beyond the channel and the immutable snapshots.
